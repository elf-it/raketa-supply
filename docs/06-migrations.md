# Миграции схемы

Схема базы живёт в Alembic. До этого она создавалась из моделей через `create_all`,
и каждое изменение требовало пересоздать базу — на боевых данных так нельзя.

## Команды

Все — из папки `backend`, с активированным окружением.

```bash
alembic upgrade head
```

```bash
alembic revision --autogenerate -m "что изменилось"
```

```bash
alembic current
```

```bash
alembic downgrade -1
```

URL базы берётся из тех же настроек, что использует приложение (`DATABASE_URL`),
и в `alembic.ini` намеренно не задан: иначе конфигурация миграций и приложения
могли бы разойтись, и миграции ушли бы не в ту базу.

## Кто и когда применяет

**Приложение миграции не применяет.** На старте оно только проверяет, что база
на последней ревизии, и падает с понятным текстом, если это не так:

```
RuntimeError: Схема базы устарела: ревизия abc123, ожидается def456.
Выполните `alembic upgrade head` в папке backend.
```

Автоматический `upgrade` при старте выглядит удобным, но при нескольких рабочих
процессах они начнут мигрировать одновременно. Применять миграции должен явный шаг
развёртывания; работать на устаревшей базе хуже, чем не запуститься.

`python -m app.seed --reset` сам откатывает схему до нуля и накатывает заново —
демо-данные должны ложиться ровно на ту схему, что получит прод.

## Что проверяется тестами

`backend/tests/test_migrations.py`:

- **Миграции совпадают с моделями.** После `upgrade head` на чистой базе
  автогенерация не должна находить отличий. Этот тест ломается ровно тогда, когда
  кто-то правит модель и забывает ревизию — главный риск перехода с `create_all`.
- Набор таблиц совпадает с метаданными моделей.
- `downgrade base` убирает всё, повторный `upgrade` идемпотентен.
- В истории ровно одна голова: две означают слияние веток, на котором
  `upgrade head` упадёт.
- Проверка ревизии на старте объясняет, что делать.
- `engine_url` сохраняет пароль: `str(engine.url)` заменяет его звёздочками,
  и Alembic с таким URL не подключился бы к Postgres.

## Особенности

**SQLite и `ALTER TABLE`.** SQLite не умеет большинство форм `ALTER TABLE`, поэтому
в `env.py` включён `render_as_batch`: Alembic пересоздаёт таблицу и переносит данные.
В ревизиях это видно по `op.batch_alter_table`.

**Кодировка `alembic.ini`.** Файл намеренно только на латинице: Alembic читает его
в кодировке локали, а на русской Windows это cp1251, и кириллица в комментариях
ломает разбор. Пояснения — в `alembic/env.py` и здесь.

**Начальная ревизия.** Одна, на всю схему целиком. Отдельных ревизий на колонки,
добавленные до перехода, нет: до этой точки схема пересоздавалась, боевых баз
не существовало. Если такая база где-то уже есть, её нужно пометить вручную:

```bash
alembic stamp head
```
