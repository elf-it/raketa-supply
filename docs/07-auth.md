# Доступ и роли

Требование приёмки по интерфейсу: «права доступа; журнал корректировок».
Реализация — `backend/app/security.py`, `backend/app/api/auth.py`,
`backend/app/api/deps.py`.

## Роли

Упорядочены по возрастанию, каждая включает предыдущую.

| Роль | Что может |
|------|-----------|
| `viewer` | Видеть всё: матрицу, закупку, потенциал, сезонность, журнал |
| `editor` | Плюс править прогноз и DIFF, массовые правки, потенциал, сезонность, закрывать неделю, запускать синхронизацию WB |
| `admin` | Плюс заводить пользователей и менять им роли |

В интерфейсе роль `viewer` видит те же числа, но без полей ввода, без отметок строк
и без панели массовых правок. Это удобство, а не защита: права проверяются на сервере
в каждом изменяющем маршруте, и прямой запрос от наблюдателя получает 403.

Открыты без входа только `/api/v1/health` и `/api/v1/auth/login`. Всё остальное
отвечает 401.

## Решения и почему так

**Токен в httpOnly-куке, а не в localStorage.** Из localStorage токен достаётся любым
исполненным на странице скриптом. Кука с `httpOnly` недоступна JS вовсе, а `SameSite=Lax`
закрывает межсайтовые POST-запросы, поэтому отдельные CSRF-токены не нужны: интерфейс
и API живут на одном источнике.

**bcrypt поверх SHA-256.** Сам bcrypt молча обрезает пароль до 72 байт. В кириллице это
всего 36 символов, то есть длинные парольные фразы совпадали бы по своему началу.
Пароль сворачивается в SHA-256, кодируется base64, и только результат уходит в bcrypt —
известная схема `bcrypt_sha256`, после которой длина входа перестаёт иметь значение.

**Автор правки берётся из сессии, а не из тела запроса.** Поля `author` в схемах больше
нет. Журнал, в котором автора подставляет клиент, ничего не доказывает — а именно на
журнал опирается разбор массовых правок.

**Ответ на неудачный вход одинаков** для несуществующей почты, неверного пароля и
отключённого аккаунта, и пароль проверяется даже для несуществующего пользователя,
чтобы ответ не был заметно быстрее. Иначе форма входа превращается в способ узнать,
кто заведён в системе.

**Последнего активного администратора нельзя разжаловать или отключить,** и никто
не может отключить сам себя: иначе системой некому управлять, и починить это
из интерфейса уже нельзя. Снять права с самого себя, пока администраторов двое,
можно — это не запирание, а решение человека, и роль вернёт коллега; экран перед
этим переспрашивает и честно предупреждает, что закроется. Запрета на сервере
намеренно нет: он сделал бы проверку «последний администратор» недостижимой —
чужую роль администратор снимает только тогда, когда администраторов больше одного.

**Учётные записи не удаляются, а отключаются.** Журнал корректировок подписан
именем автора, и эта подпись должна пережить увольнение: удаление пользователя
превратило бы историю правок в набор ссылок в пустоту. Отключённый не входит
в систему, а его доступ прекращается сразу.

**Отключённый пользователь теряет доступ сразу,** не дожидаясь истечения токена:
роль и активность проверяются по базе на каждом запросе, а не берутся из токена.

**Свой пароль человек меняет сам, но с прежним паролем на руках.** Прежний пароль
спрашивается не для проверки памяти: сессия могла остаться открытой на чужой машине,
и без него уведённой куки хватало бы, чтобы забрать учётную запись насовсем. Отказ
отвечает 409, а не 401: 401 интерфейс понимает как «сессия кончилась» и выбрасывает
человека на экран входа вместе с заполненной формой, а сессия здесь как раз в порядке.

**Смена пароля закрывает остальные сессии этого человека.** Иначе смена не решает
ровно ту задачу, ради которой её делают: уведённая кука жила бы ещё двенадцать часов.
У пользователя хранится отметка `password_changed_at`, и токен, выданный раньше неё,
больше не принимается. Сравнение идёт в целых секундах, потому что в целых секундах
JWT хранит `iat`; из-за этого сессия, выданная в ту же секунду, что и смена, уцелеет.
Та вкладка, из которой пароль меняли, получает новую куку и продолжает работать —
как и администратор, задавший новый пароль самому себе.

**Неудачные попытки входа считаются.** Без счётчика перебор замедляет только стоимость
bcrypt — это сотни попыток в минуту с одной машины. Счётчик ведётся по паре «почта +
адрес» (а не по почте, иначе он сам стал бы способом заблокировать коллегу) и отдельно
по адресу — на случай, когда перебирают не пароль, а почту. После лимита вход отвечает
429 и `Retry-After`, причём и с верным паролем: иначе лимит обходился бы очередной
попыткой. Удачный вход снимает счётчик пары. Устройство и пределы применимости —
`backend/app/ratelimit.py`.

## Настройки

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `SECRET_KEY` | небезопасное значение для отладки | Ключ подписи сессионных токенов |
| `SESSION_TTL_HOURS` | 12 | Срок жизни сессии |
| `COOKIE_SECURE` | `false` | Отдавать куку только по HTTPS |
| `LOGIN_MAX_ATTEMPTS` | 10 | Неудачных попыток на пару «почта + адрес» за окно |
| `LOGIN_MAX_ATTEMPTS_PER_ADDRESS` | 60 | Неудачных попыток с адреса на все учётные записи |
| `LOGIN_WINDOW_MINUTES` | 15 | Окно, за которое считаются попытки, и срок запрета |

Вне отладки (`DEBUG=false`) приложение **не стартует**, если `SECRET_KEY` остался
значением по умолчанию или `COOKIE_SECURE=false`. Токен, подписанный общеизвестным
ключом, подделывается кем угодно, а кука по открытому HTTP перехватывается.

Сгенерировать ключ:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

## Пользователи

Демонстрационные учётные записи заводит сид (`backend/app/seed.py`, список
`DEMO_USERS`) — по одной на каждую роль. Пароли лежат в репозитории, поэтому
существуют только для локального запуска.

Боевых пользователей заводит администратор на вкладке **Пользователи**
(`frontend/src/components/UsersPage.tsx`). На экране: список учётных записей
с ролью, доступом и датой заведения; форма «завести» (почта, имя, роль, первый
пароль); правка имени прямо в строке; смена роли списком; кнопки «Отключить» /
«Включить»; «задать новый пароль».

Вкладка показывается только администратору, но это удобство: ручки `/auth/users`
закрыты ролью на сервере, и прямой запрос от редактора получает 403.

Пароль администратор задаёт и передаёт человеку лично — восстановить его система
не умеет и не должна: хранится только хеш. «Забыл пароль» решается тем же
«задать новый»: старый перестаёт работать сразу.

Свой пароль человек меняет сам — кнопка **Сменить пароль** в шапке
(`frontend/src/components/ChangePassword.tsx`). Нужен прежний пароль; новый —
от восьми символов, с повтором, чтобы опечатка в скрытом поле не обнаружилась
при следующем входе. Та же ручка годится и для командной строки:

```bash
curl -X POST http://localhost:8000/api/v1/auth/me/password -H 'Content-Type: application/json' --cookie 'raketa_session=<своя кука>' -d '{"current_password":"<прежний>","new_password":"<новый>"}'
```

То же самое из командной строки, если интерфейс недоступен:

```bash
curl -X POST http://localhost:8000/api/v1/auth/users -H 'Content-Type: application/json' --cookie 'raketa_session=<кука администратора>' -d '{"email":"name@company.ru","full_name":"Имя Фамилия","role":"editor","password":"<пароль>"}'
```

Миграция пользователей не создаёт: заводить учётные записи — не её дело.

## Первый администратор и потерянный доступ

В пустой базе администратора нет, а экран пользователей сам требует прав
администратора — замкнутый круг, из которого демонстрационный сид не выход:
он принесёт вместе с людьми выдуманный каталог. Поэтому есть отдельная команда
(`app/admin.py`), работающая прямо с базой:

```bash
python -m app.admin anna@example.com "Анна Петрова"
```

Пароль она генерирует и печатает один раз либо берёт из переменной
`RAKETA_ADMIN_PASSWORD` — тогда не печатает вовсе. Аргументом он не передаётся
намеренно: остался бы в истории оболочки и в списке процессов, который на машине
виден всем.

Этой же командой возвращают доступ, когда пароль потерял **единственный**
администратор: отдать ему новый некому — ручка «задать новый пароль» закрыта
ролью администратора. Команда возвращает роль, включает запись и задаёт пароль
заново, выставляя `password_changed_at`, то есть прежние сессии этого человека
закрываются сразу — если доступ восстанавливают после утечки, чужая кука не
должна дожить до конца своих часов. Проверено тестами
(`backend/tests/test_admin_cli.py`).

Доступ к этой команде равен доступу к серверу и базе — отдельной защиты у неё
нет и быть не может: тот, кто может её запустить, может и переписать хеш руками.

## Чего не хватает

- Сброса пароля по почте нет и не будет без почтового сервиса: забытый пароль
  задаёт заново администратор.
- Счётчик попыток входа живёт в памяти процесса. За несколькими воркерами лимит
  делится на их число, при перезапуске обнуляется, а за обратным прокси без
  проброса адреса все клиенты выглядят одним — тогда работает только счётчик
  по адресу, и его порог поднимают. В проде нужен общий счётчик (Redis) или
  ограничение на уровне прокси (задача G-12).
- Требований к самому паролю, кроме длины от восьми символов, нет: ни словаря
  частых паролей, ни обязательной смены по сроку.
- Привязки прав к магазинам: роль действует на всю систему сразу.
