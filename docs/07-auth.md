# Доступ и роли

Требование приёмки по интерфейсу: «права доступа; журнал корректировок».
Реализация — `backend/app/security.py`, `backend/app/api/auth.py`,
`backend/app/api/deps.py`.

## Роли

Упорядочены по возрастанию, каждая включает предыдущую.

| Роль | Что может |
|------|-----------|
| `viewer` | Видеть всё: матрицу, закупку, потенциал, сезонность, журнал |
| `editor` | Плюс править прогноз и DIFF, массовые правки, потенциал, сезонность, закрывать неделю, запускать синхронизацию WB |
| `admin` | Плюс заводить пользователей и менять им роли |

В интерфейсе роль `viewer` видит те же числа, но без полей ввода, без отметок строк
и без панели массовых правок. Это удобство, а не защита: права проверяются на сервере
в каждом изменяющем маршруте, и прямой запрос от наблюдателя получает 403.

Открыты без входа только `/api/v1/health` и `/api/v1/auth/login`. Всё остальное
отвечает 401.

## Решения и почему так

**Токен в httpOnly-куке, а не в localStorage.** Из localStorage токен достаётся любым
исполненным на странице скриптом. Кука с `httpOnly` недоступна JS вовсе, а `SameSite=Lax`
закрывает межсайтовые POST-запросы, поэтому отдельные CSRF-токены не нужны: интерфейс
и API живут на одном источнике.

**bcrypt поверх SHA-256.** Сам bcrypt молча обрезает пароль до 72 байт. В кириллице это
всего 36 символов, то есть длинные парольные фразы совпадали бы по своему началу.
Пароль сворачивается в SHA-256, кодируется base64, и только результат уходит в bcrypt —
известная схема `bcrypt_sha256`, после которой длина входа перестаёт иметь значение.

**Автор правки берётся из сессии, а не из тела запроса.** Поля `author` в схемах больше
нет. Журнал, в котором автора подставляет клиент, ничего не доказывает — а именно на
журнал опирается разбор массовых правок.

**Ответ на неудачный вход одинаков** для несуществующей почты, неверного пароля и
отключённого аккаунта, и пароль проверяется даже для несуществующего пользователя,
чтобы ответ не был заметно быстрее. Иначе форма входа превращается в способ узнать,
кто заведён в системе.

**Последнего активного администратора нельзя разжаловать или отключить,** и никто
не может отключить сам себя: иначе системой некому управлять, и починить это
из интерфейса уже нельзя.

**Отключённый пользователь теряет доступ сразу,** не дожидаясь истечения токена:
роль и активность проверяются по базе на каждом запросе, а не берутся из токена.

## Настройки

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `SECRET_KEY` | небезопасное значение для отладки | Ключ подписи сессионных токенов |
| `SESSION_TTL_HOURS` | 12 | Срок жизни сессии |
| `COOKIE_SECURE` | `false` | Отдавать куку только по HTTPS |

Вне отладки (`DEBUG=false`) приложение **не стартует**, если `SECRET_KEY` остался
значением по умолчанию или `COOKIE_SECURE=false`. Токен, подписанный общеизвестным
ключом, подделывается кем угодно, а кука по открытому HTTP перехватывается.

Сгенерировать ключ:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

## Пользователи

Демонстрационные учётные записи заводит сид (`backend/app/seed.py`, список
`DEMO_USERS`) — по одной на каждую роль. Пароли лежат в репозитории, поэтому
существуют только для локального запуска.

Боевых пользователей заводит администратор:

```bash
curl -X POST http://localhost:8000/api/v1/auth/users -H 'Content-Type: application/json' --cookie 'raketa_session=<кука администратора>' -d '{"email":"name@company.ru","full_name":"Имя Фамилия","role":"editor","password":"<пароль>"}'
```

Миграция пользователей не создаёт: заводить учётные записи — не её дело.

## Чего не хватает

- Экрана управления пользователями в интерфейсе: API готов, страницы нет.
- Сброса пароля и смены своего пароля.
- Ограничения частоты попыток входа — сейчас перебор ничем не замедляется,
  кроме стоимости bcrypt.
- Привязки прав к магазинам: роль действует на всю систему сразу.
