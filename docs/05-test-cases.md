# Тест-кейсы приёмки

Приёмка — это не «посмотреть, что всё открывается», а пройти согласованный набор
проверок и получить одинаковый результат у исполнителя и у заказчика. Здесь этот
набор: десять кейсов, у каждого номер **ПР-N**.

Главное свойство набора — он **исполняется**. Каждому кейсу соответствует ровно
один тест в `backend/tests/test_acceptance.py` с тем же номером, и отдельная
проверка следит, чтобы в документе не осталось кейса без теста. Документ приёмки,
который разошёлся с поведением системы, хуже, чем его отсутствие: по нему
принимают.

```bash
cd backend && pytest -k acceptance     # весь набор
cd backend && pytest -k pr_05          # один кейс
```

Кейсы написаны от лица человека: вход через API на демонстрационных данных,
проверка того, что увидит заказчик на экране.

## Набор

| № | Кейс | Что проверяет | Чего ждёт от заказчика |
|---|------|---------------|------------------------|
| ПР-1 | Кабинеты не смешиваются | Строка принадлежит своему кабинету, сумма по кабинетам равна выборке, повторная загрузка не удваивает факты | Проверку на боевых ключах (Q-3) |
| ПР-2 | Правка прогноза доходит до стока и закупки и переживает пересчёт | Число человека становится исходным спросом, сток и закупка считаются по нему, пересчёт правку не стирает | — |
| ПР-3 | Статусы OVER/SHORT и DIFF следуют правилам | Отбор по статусу совпадает со значками строк, у SHORT есть непокрытый спрос, DIFF меняет прогноз пропорционально | **Пороги и трактовку DIFF (Q-1)** |
| ПР-4 | Итоги трёх уровней сходятся | Итог недели одинаков по магазинам, категориям и артикулам; сумма строк равна итогу | — |
| ПР-5 | Потребность → заказ → товар в пути | Черновик расчёту не виден, размещение уменьшает потребность, отмена возвращает | Набор статусов заказа (Q-11) |
| ПР-6 | Новая цена меняет закупку, но не сумму заказа | Закупка считается по новой цене, строка документа держит снимок прежней, расхождение видно | По какой цене считать заказ, который придёт после подорожания (Q-14) |
| ПР-7 | Заведённая позиция считается, снятая — нет | Товар в кабинете появляется в матрице и закупке; снятый с продажи выпадает из расчёта, прошлое остаётся | Откуда берётся номенклатура (Q-15) |
| ПР-8 | Роль «просмотр» ничего не меняет | Чтение работает везде, любая запись — 403, проверка на сервере | — |
| ПР-9 | Выгрузка в Excel и возврат правок | Правка числа в файле возвращается в систему: сначала предпросмотр, потом применение | Правило разрешения конфликтов (Q-13) |
| ПР-10 | Сбой загрузки виден снаружи | Готовность отвечает 503 и называет причину, живость остаётся зелёной | Куда доставлять алерт (Q-16) |
| ПР-11 | ROI сравнивает позиции, но ничего не заказывает | Цена меняет ROI, но не количество, дату и приход; без заказа ROI пуст, а не ноль; в выгрузке та же колонка | **Определение ROI и нужно ли вычитать комиссию (Q-2)** |

Колонка «чего ждёт от заказчика» — не про незаконченный кейс: все десять
выполняются уже сейчас. Она про то, что в кейсе проверяется **правило**, а число
или трактовка в нём — наше допущение, и его нужно подтвердить.

## Соответствие критериям приёмки из ТЗ

| Критерий | Кейсы | Статус |
|----------|-------|--------|
| № 1. Кабинеты WB загружаются без смешивания магазинов | ПР-1 | выполнен на фикстурах; на боевых ключах не проверен (Q-3) |
| № 2. Правка прогноза пересчитывает остатки и закупку, ручные правки сохраняются | ПР-2, ПР-9 | выполнен |
| № 3. OVER/SHORT, DIFF и закупка совпадают с тест-кейсами | ПР-3, ПР-5, ПР-6 | правила выполнены, **числа не согласованы** (Q-1, Q-2) |
| № 4. Итоги по уровням согласованы, нет двойного учёта | ПР-4 | выполнен |

## Что нужно от заказчика, чтобы закрыть критерий № 3

Для каждого пункта нужен фрагмент действующего файла: вход (базовый потенциал,
сезонность, факты, поставки, параметры закупки) и ожидаемый выход. Такой
фрагмент превращается в ещё один кейс ПР-N и ложится рядом с остальными.

1. **DIFF на реальных данных.** Неделя, где DIFF отличается от 100 %, с объяснением,
   откуда взялось значение. Сейчас DIFF — процентный множитель, это допущение (Q-1).
2. **Граница OVER.** Позиция, которую заказчик считает затоваренной, и соседняя,
   которую не считает. Из пары выводится порог (сейчас 12 недель покрытия).
3. **Граница SHORT.** Позиция в дефиците и позиция, где дефицит ожидается, но тревоги
   нет. Сейчас окно — 8 недель, это допущение.
4. **Полный расчёт закупки по одной позиции.** Дата заказа и количество, посчитанные
   в текущем файле, чтобы сверить округление до PCB и применение MOQ.
5. **ROI.** Определение заказчика и пример расчёта (Q-2). Колонка есть, формула — наша
   (раздел 5.1 спецификации): нужно подтвердить, ту ли величину заказчик называет ROI
   и вычитать ли комиссию маркетплейса, логистику и хранение.
6. **Дефицит и восстановление.** Недели, где товар кончился, пришла поставка и продажи
   восстановились: проверка, что исходный спрос не обнулился.
7. **Товар в нескольких кабинетах.** Ожидаемые итоги по магазинам и по категориям —
   проверка трактовки из вопроса Q-4.
8. **Переход через конец года.** Неделя 52/53 и первая неделя января: как заказчик
   нумерует недели и как считает сезонность.

## Что ещё проверяется автоматически

Кейсы приёмки — верхний слой. Под ними 318 тестов, которые проверяют то, на чём
кейсы стоят; запуск: `cd backend && pytest`.

| Файл | Что покрывает |
|------|---------------|
| `test_weeks.py` | ISO-недели, переход через границу года, 53-я неделя |
| `test_series.py` | Исходный и адаптированный прогноз, сток, DIFF, приоритет ручной правки, статусы; два теста воспроизводят числа прямо с макета ТЗ (стр. 3) |
| `test_purchase.py` | Страховой запас, дата заказа, MOQ, PCB, партии в пути, просроченные заказы, стоимость и объём |
| `test_aggregate.py`, `test_matrix_paging.py`, `test_matrix_row.py` | Согласованность уровней, отсутствие двойного учёта, окна строк, точечное обновление |
| `test_orders.py`, `test_order_edit.py`, `test_order_add_line.py` | Жизненный цикл заказа, правка черновика, запрет правки размещённого |
| `test_prices.py` | История цен: новая не стирает прежнюю, карточка и история не расходятся |
| `test_catalog_admin.py`, `test_catalog_import.py` | Ведение справочников, загрузка номенклатуры файлом, круговая проверка «выгрузили — загрузили» |
| `test_matching.py` | Несопоставленные номенклатуры, поиск дублей, слияние товаров |
| `test_exports.py`, `test_matrix_import.py` | Книги Excel и возврат правок, конфликты |
| `test_auth.py`, `test_login_ratelimit.py`, `test_admin_cli.py` | Роли, сессии, счётчик попыток входа, первый администратор |
| `test_observability.py`, `test_sync_cli.py` | Логи, номер запроса, готовность, загрузка по расписанию |
| `test_migrations.py`, `test_deploy_config.py` | Схема не расходится с моделями, боевая сборка — с настройками |
| `test_calc_cache.py`, `test_seed_scale.py` | Годность кэша расчёта, каталог на тысячах позиций |

## Как добавить кейс

1. Строка в таблице выше с очередным номером ПР-N.
2. Тест `test_pr_NN_...` в `backend/tests/test_acceptance.py`: в описании —
   «дано / когда / тогда», в коде — путь через API и уборка за собой.
3. Номер в список `test_every_case_from_the_document_is_runnable`, чтобы кейс
   без теста не прошёл незамеченным.
