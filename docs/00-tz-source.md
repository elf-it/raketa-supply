# ТЗ v0.5 от 09.11.2026 — расшифровка исходника

Исходник: PDF «РАКЕТА / КРАТКОЕ ТЗ v0.5», 5 страниц. Текст извлечён, блок-схемы и макеты
на страницах 2–4 были векторными и переписаны вручную. Это дословная расшифровка,
без интерпретаций — интерпретации в `03-calc-spec.md`.

## Стр. 1. Цель проекта

> Перенести действующие расчёты в веб-приложение с базой данных и загрузкой WB.
> Пользователь выбирает один из трёх уровней просмотра: магазины, категории или артикулы.

Что должна уметь система:

1. **Прогноз продаж и остатки.** Единая недельная матрица: исходный и адаптированный
   прогнозы, реальный и адаптированный сток, факты, поставки, OVER/SHORT и DIFF.
2. **Закупочная потребность.** Автоматический расчёт даты и объёма заказа: спрос,
   остатки, уже заказанные партии, lead time, MOQ, PCB, coverage, safety и ROI.
3. **Базовый потенциал и сезонность.** Отдельные страницы редактирования базового
   потенциала SKU и недельных коэффициентов сезонности категорий.
4. **Факты и справочники.** История заказов, выкупов, продаж и остатков; единая база
   товаров, цен, категорий и поставщиков; загрузка из API WB.

В первой рабочей версии — все действующие магазины WB одновременно. Число и перечень
кабинетов уточняются перед подключением API. Вторая очередь: Ozon, Яндекс Маркет,
другие площадки и финансовое планирование оплат поставщикам.

**Ключевой принцип.** Изменение прогноза → автоматический пересчёт остатков, рисков
дефицита и закупочной потребности. Исходный спрос сохраняется даже при отсутствии
доступного товара: нельзя превращать нулевые продажи из-за шортажа в нулевую потребность.

## Стр. 2. Блок-схемы

**01 Архитектура и поток данных**

```
ИСТОЧНИКИ            →  ЕДИНАЯ БАЗА        →  РАСЧЁТНОЕ ЯДРО        →  ВЕБ-ИНТЕРФЕЙС
API WB · справочники    товары · магазины     прогноз · DIFF           три режима:
поставки · цены         история · стоки       остатки                  магазин /
                                              потребность в закупке    категория / артикул
```

**02 Прогноз → остатки → потребность**

```
Базовый потенциал  →  Сезонность       →  Исходный прогноз   →  DIFF + доступность  →  Адаптированный
(спрос по SKU)        (коэфф. недель)     (спрос без лимита      (OVER / SHORT ·        (прогноз продаж)
                                           стока)                 приходы)
                                              ↓                                             ↓
                                       План закупок                                Расчёт будущего стока
                                       (по исходному спросу                        (сценарий спроса
                                        и запасам)                                  и адаптации)
```

**03 Расчёт закупки**

```
ВХОДНЫЕ ДАННЫЕ          →  ОГРАНИЧЕНИЯ               →  РАСЧЁТ                 →  РЕЗУЛЬТАТ
спрос · остатки ·          lead time · MOQ ·            дата заказа ·             штуки · стоимость ·
товары в пути              PCB · safety                 количество                м³ · приход
```

> **Важно:** адаптированный прогноз ограничивает реализуемые продажи доступным стоком;
> исходный прогноз остаётся источником планового спроса для закупок. Алгоритм DIFF
> и правила статусов переносятся из действующих файлов после проверки.

## Стр. 3. UX-концепция: три режима

> Не дерево строк: один экран с переключателем уровня. Каждый режим показывает свою
> агрегацию недельных показателей.

На макете — одна таблица, переключатель `Магазины | Категории | Артикулы`, колонки
недель `W46 2026 … W49 2026`, первая колонка «МАГАЗИН / КАТЕГОРИЯ / ПОКАЗАТЕЛЬ»,
внизу строка итогов.

- Уровень «Магазины»: строки `Магазин 01/02/03`, итог `ИТОГО ПО WB`.
- Уровень «Категории»: контекст «Магазин: Магазин 01», строки `Лампы / Рации / Аксессуары`,
  итог `ИТОГО ПО МАГАЗИНУ`. Сумма категорий = значение магазина на предыдущем уровне.
- Уровень «Артикулы»: контекст «Магазин 01 · Категория: Лампы», показан `SKU 2041904540146 • A10 H7`,
  строки показателей: `Исходный прогноз продаж`, `Адаптированный прогноз продаж`,
  `Реальный сток общий`, `Адаптированный сток общий`.

> Что важно в интерфейсе: переключение уровней без раскрытия дерева; отдельные таблицы
> по магазинам, категориям и SKU; фильтры; редактирование прогнозов на уровне артикула;
> массовые корректировки; графики.

> Числа на макете — демонстрационные. Итоги агрегируются по выбранному уровню;
> нельзя повторно учитывать один физический остаток.

## Стр. 4. UX-референс: существующий макет заказчика

Экран «Недельный план продаж», подзаголовок «План, факт, новый прогноз и сток
в единой недельной матрице». Кнопки `Сбросить` и `Сохранить`.

Фильтры: поиск «Товар или артикул», селект магазина, селект площадки (Wildberries),
селект ниши («Все ниши»).

KPI-плитки: `Последняя завершённая — W36 2026`; `Выполнение плана · 4 недели — 101% (+6 шт.)`;
`Новый прогноз W37 — 251 шт.`; `Shortage — 8 SKU до поступления`.

Таблица «Прогноз по артикулам», подпись: «Новый прогноз редактируется в таблице.
После закрытия недели он фиксируется как её план.» Легенда: Факт · Прогноз · Поступление.

Колонки сгруппированы по месяцам (Август 2026, Сентябрь 2026, Октябрь 2026),
внутри — недели W33…W45. Текущая неделя W36 выделена.

Структура строк: на каждый товар четыре строки показателей —
`План / исходный прогноз`, `Факт / новый прогноз`, `DIFF`, `Сток на конец недели`.
Первая колонка — название товара, артикул, бейдж категории (A / C) и бейдж статуса
(`Overstock`, `Shortage`).

Детали ячеек: прошлые недели — числа без рамки (факт), отклонение вниз подсвечено
красным; будущие недели — редактируемые поля; под числом подпись `+250` / `+40` / `+30`
(поступление); при упоре в сток подпись `лимит стока` и значение падает (35 → 7 → 0 → 0);
DIFF — поле ввода со значением `100` и суффиксом `%`, на закрытых неделях прочерк.

## Стр. 5. Границы MVP и приёмка

> MVP и дизайн интерфейса разрабатывает специалист по снабжению. Кандидат оценивает
> архитектуру, интеграции и доведение системы до стабильной эксплуатации.

Минимально необходимый рабочий результат:

- **Данные и интеграции:** все действующие кабинеты WB; стабильная синхронизация;
  история; сопоставление SKU; контроль дублей и ошибок API.
- **Расчётное ядро:** исходный/адаптированный прогноз; реальный/адаптированный сток;
  DIFF; поставки; расчёт закупки и ограничений.
- **Интерфейс:** переключение уровней магазины/категории/артикулы; редактирование
  и массовые изменения; графики; права доступа; журнал корректировок.

Порядок реализации: 1) MVP и UX/UI → 2) технический аудит (архитектура, база, API,
тест-кейсы) → 3) backend и интеграции → 4) сверка и запуск.

**Критерии приёмки**

1. Данные всех стартовых кабинетов WB загружаются без смешивания магазинов.
2. Изменение прогноза пересчитывает зависимые остатки и закупку; ручные правки сохраняются.
3. Статусы OVER/SHORT, DIFF и закупочные расчёты совпадают с согласованными тест-кейсами.
4. Итоги по выбранным уровням (магазин, категория, SKU) согласованы между собой;
   двойного учёта запасов нет.

От кандидата ожидают: оценку архитектуры MVP; серверные расчёты и API WB; план доработки
прототипа; сроки и бюджет; тестирование, документацию, развёртывание и сопровождение.
