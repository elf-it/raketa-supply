# Архитектура

## Общая схема

```
┌───────────────┐      ┌─────────────────────────────────────────────┐      ┌──────────────┐
│  API WB       │      │                 BACKEND                      │      │  FRONTEND    │
│  (кабинеты)   │─────▶│  integrations/wb  →  models (PostgreSQL)      │◀────▶│  React + TS  │
│  ручной ввод  │      │                         ↓                     │ REST │  Vite        │
└───────────────┘      │                   calc/ (чистое ядро)         │      └──────────────┘
                       │                         ↓                     │
                       │                   api/ (FastAPI)              │
                       └─────────────────────────────────────────────┘
```

Соответствует схеме 01 из ТЗ: источники → единая база → расчётное ядро → веб-интерфейс.

## Решения и почему так

**Расчётное ядро отделено от БД.** `app/calc/` не импортирует SQLAlchemy и не знает
про HTTP. На вход — простые dataclass-структуры, на выход — результат расчёта. Это даёт
две вещи, которые прямо требует ТЗ: тест-кейсы приёмки гоняются как обычные юнит-тесты
без базы, и сверка с действующими Google Sheets делается на тех же структурах.

**Минимальная расчётная единица — пара (магазин, товар).** Один физический остаток
принадлежит ровно одной паре. Из этого автоматически следует критерий приёмки № 4:
агрегация по магазинам и по категориям — это разные группировки одного множества пар,
поэтому остаток не может попасть в итог дважды.

**Неделя — ISO-неделя строкой `2026-W46`.** Сортируется лексикографически, однозначно
отображается в понедельник, переносится в JSON без часовых поясов.

**Расчёт — на лету, не в таблице.** Хранятся только входы: базовый потенциал,
сезонность, факты, поставки, ручные правки. Всё производное считается при запросе.
Иначе «изменение прогноза → автоматический пересчёт» превращается в инвалидацию кэшей
и рассинхрон. Если упрёмся в производительность — появится материализация на уровне
сервиса, но не раньше, чем будут известны реальные объёмы (Q-9).

**Факты по неделям, а не по дням.** Вся продуктовая логика недельная. Дневная
гранулярность из WB агрегируется на входе; сырые дневные данные можно будет сложить
отдельной таблицей, когда это понадобится.

**Загрузка WB — идемпотентный upsert.** Повторный прогон того же периода не плодит
дубли: ключ `(store_id, product_id, week)`.

**График строится из тех же строк, что и таблица.** Отдельной ручки под графики нет:
матрица уже отдаёт все показатели по неделям, и `RowChart` рисует их прямо из выбранных
строк. Побочный эффект важнее экономии запроса — правка прогноза перерисовывает график
теми же числами, которые видит таблица, и разойтись им негде.

**Сравнение строк — другой график, а не тот же с добавленными рядами.** Одна строка
показана столбиками с разбором на план, факт, адаптированный прогноз и непокрытую часть;
четыре таких набора в каждой неделе читать было бы нечем. Поэтому при двух и более
строках график переключается на линии: по линии спроса и линии стока на строку, без
штриховки и меток поставок. Спрос в этом режиме — исходный прогноз, а не адаптированный:
адаптированный обрезан стоком и на дефицитной позиции падает в ноль, так что сравнивалась
бы способность обслужить спрос, а не сам спрос.

**Шкала сравнения — три режима, а не два.** На общей шкале в штуках позиция в десятки
штук лежит на нуле рядом с позицией в тысячи, и сравнивать формы нечем; доля
от собственного пика формы показывает, но числа превращаются в проценты, и объём
теряется. Поэтому для двух строк есть третий режим: у каждой своя шкала в штуках,
левая и правая, подписи окрашены в цвет своей строки. Платой идёт то, что высоты
линий между собой не сравнимы, а точка их пересечения ничего не значит, — это сказано
и под графиком. Ноль у обеих осей сведён на одну высоту: иначе линия одной строки
пересекала бы нулевую черту там, где у неё ещё есть остаток, и «ниже нуля — дефицит»
перестало бы читаться. Третьей оси места нет, поэтому режим живёт только на паре строк:
с третьей строкой график сам показывает доли и говорит об этом, а выбор человека
сохраняется до того, как лишнюю строку снимут.

**Выгрузка — XLSX, а не CSV.** CSV в русском Excel открывается то в одной кодировке,
то в другой, и разделитель зависит от настроек системы: файл, который получатель
открывает в одну колонку с кракозябрами, бесполезен. Настоящая книга (`openpyxl`)
снимает вопрос целиком. Сборка книг живёт в `services/order_export.py`
и `services/matrix_export.py` и ничего не знает про HTTP; общие стили и табличная
механика — в `services/xlsx.py`, заголовок ответа с именем файла по RFC 5987 —
в `api/responses.py`, один на все выгрузки.

**Выгрузка собирается из того же сервиса, что и экран.** `/matrix/export` зовёт
`build_matrix` с теми же фильтрами, что и `/matrix`, а `/purchase/export` —
`build_purchase_plan`. Отдельного «отчётного» расчёта нет и быть не должно: файл,
который разойдётся с экраном на пару штук, обесценит сверку с действующими Google
Sheets, ради которой выгрузка и нужна. Округление в файле — такое же, как на экране:
если в интерфейсе никто не видел хвоста двоичной дроби, в файле ему тоже неоткуда
взяться.

**Обратная загрузка берёт из файла только расхождения.** В выгрузке стоит весь
прогноз выборки, а не только исправленное, и принять файл целиком означало бы
превратить каждую ячейку в ручную правку: расчёт по потенциалу и сезонности встал
бы намертво — тихо, по всей выборке и без единого сообщения. Поэтому каждое число
сравнивается с тем, что система показывает сейчас, и в работу идёт только то, что
разошлось. Читается одна строка показателя — «План / исходный прогноз»: остальные
производные, и спорить с расчётом им нечем. Уровни групп не загружаются вовсе —
у строки магазина нет однозначного разложения правки по позициям.

**Чужую правку файл не затирает.** Расхождение значит одно из двух: человек
исправил ячейку в файле или кто-то изменил её в системе, пока файл правили.
По самому числу это неразличимо, поэтому в шапке файла стоит момент выгрузки
(в UTC и с секундами — он сравнивается с отметками журнала, а округление до минуты
плодило бы ложные конфликты). Если после этого момента в журнале есть правка той же
ячейки, расхождение показывается конфликтом и не применяется — **[ДОПУЩЕНИЕ, Q-13]**.
Файл уходит на сервер дважды: сначала разбор, который ничего не пишет, потом
применение. Состояния между ними сервер не держит — его негде согласовать между
воркерами, а пересчитать разбор заново дешевле, чем ошибиться.

**В выгрузке матрицы строки не склеиваются вертикально.** На экране показатели одной
позиции сидят под одним названием, и объединённые ячейки повторили бы эту картинку,
но они ломают сортировку и автофильтр — а файл открывают именно чтобы отфильтровать
и отсортировать. Левые колонки повторяются в каждой строке показателя, зато над
таблицей стоит автофильтр, и итоги оставлены ниже его диапазона, чтобы не уезжали
в середину при сортировке.

**В таблице живут только видимые строки.** Блок одной позиции — это шесть строк
показателей на полсотни недель, то есть триста ячеек. На тысяче позиций браузер
получал полмиллиона узлов: вкладка занимала гигабайт, а один щелчок по строке стоил
одиннадцати секунд пересборки. Поэтому в DOM остаются только блоки, попавшие в окно
прокрутки, а место остальных занимают две пустые строки-распорки нужной высоты — полоса
прокрутки показывает настоящую длину таблицы. Высота блока измеряется у отрисованных
и считается одинаковой для всех: на уровне артикулов блоки одного строения, и это
единственное место, где такое допущение сделано. На уровнях групп виртуализации нет —
строк там столько, сколько магазинов и категорий, а высота зависит от длины названия.
Цена решения: поиск по странице и печать видят только то, что сейчас в DOM; поиск
по артикулу в системе свой, серверный, а печать идёт через выгрузку в XLSX.
Замеры на 1080 позициях × 34 недели: 566 000 узлов → 5 000, перерисовка 11,5 с → 0,06 с,
память вкладки 1030 МБ → 24 МБ. Проверять это на демо-каталоге из восемнадцати позиций
нечем, поэтому у сида есть ключ `--scale`, который размножает каталог.

**Строки матрицы отдаются окнами, итоги — нет.** Виртуализация решает, сколько
строк живёт в DOM, но по сети до неё приезжала вся выборка: на 1080 позициях это
6,5 МБ JSON. Поэтому `/matrix` принимает `offset` и `limit`, а экран берёт страницы
по двести строк и просит следующую, когда прокрутка подошла к концу загруженного.
Режутся только строки: итоги, KPI и счётчики считаются по всей выборке, иначе итог
под таблицей менялся бы от того, насколько человек успел прокрутить. По той же
причине в ответе приходит список пар всей выборки — по нему работают «отметить все»
и массовая правка, а не по загруженной странице; это идентификаторы, десяток
килобайт на тысячу позиций. Страницы идут подряд от начала выборки, и это не
случайность: правка прогноза пересчитывает сток, статусы и итоги, а вернуть экран
в прежний вид одним запросом можно только пока загруженное — префикс.

Чего это не лечит: расчёт. Ряды всё равно собираются по всем парам выборки —
без них не посчитать ни итоги, ни отбор по статусу. Замеры на 1080 парах × 34 недели:
ответ 6,5 МБ → 1,2 МБ, время в браузере 1,08 с → 0,88 с, из которых 0,65 с — сборка
на сервере, одинаковая с окном и без него. На loopback выигрыш выглядит скромно,
потому что пять лишних мегабайт тут бесплатны; на реальной сети платит за них
пользователь. Эти 0,65 с и стали следующей задачей — см. ниже.

**Кэш расчёта — по парам, а не по экранам.** Пара (магазин, товар) считается
независимо от остальных, поэтому её посчитанный недельный ряд обслуживает все три
уровня просмотра, любые фильтры и любую страницу: уровни — это лишь разные
группировки одного множества рядов. Кэш по готовому экрану пришлось бы выбрасывать
целиком на каждую правку ячейки, то есть ровно в том режиме, в котором с системой
и работают.

Годность записи решают номера версий из базы: у пары свой, на общее (сезонность,
категория товара, настройки расчёта) — один на всех. Память процесса здесь только
хранилище, и это главное: правка, прошедшая через соседний воркер, поднимет номер
в базе, и чужая запись перестанет подходить сама — рассылать сообщения между
процессами не нужно. Номера поднимает слушатель ORM, а не вызовы по месту: забытый
вызов дал бы не медленный экран, а молча устаревшие числа. Матрица на 1080 парах
отвечает за 0,14 с вместо 0,88 с, правка ячейки пересчитывает одну пару.
Подробности и пределы — [08-performance.md](08-performance.md).

**Ответ на правку — одна строка с итогами.** Пересчитать мало: экран ещё должен
показать пересчитанное, а он перечитывал всё загруженное, потому что не знал,
какая часть изменилась. Изменилась же ровно одна строка — пары независимы.
Поэтому у матрицы есть `/matrix/row`: та же выборка с теми же фильтрами, но строк
в ответе не больше одной, а итоги, KPI и счётчики — как обычно, по всей выборке.
На загруженной тысяче позиций правка стоит 22 КБ вместо 6,5 МБ. Строка приходит
вместе со своим местом в выборке; если её в ответе нет — отбор по статусу
вытолкнул её, за ней сдвинулись остальные, и экран перечитывает выборку целиком.

**Своя отрисовка на SVG вместо библиотеки графиков.** Нужен один специфический график:
столбики спроса с заштрихованной частью, которую не покрывает сток, плюс линия стока,
уходящая ниже нуля. Это ровно та логика, ради которой написано ядро, и подгонять под неё
чужой компонент дороже, чем нарисовать полсотни SVG-элементов. Фронтенд остаётся без
зависимостей сверх React.

## Слои бэкенда

| Слой | Папка | Зависит от |
|------|-------|-----------|
| Чистое ядро | `app/calc/` | ничего, только stdlib |
| Модели и БД | `app/models.py`, `app/db.py`, `app/revisions.py` | SQLAlchemy |
| Сервисы | `app/services/` | модели + ядро |
| HTTP API | `app/api/` | сервисы |
| Интеграции | `app/integrations/` | модели |

Зависимости идут только вниз. `calc` ничего не импортирует из проекта.

## Хранилище

PostgreSQL в проде и в compose. Для локального старта и для тестов — SQLite:
`DATABASE_URL` по умолчанию `sqlite:///./raketa.db`, так что `uvicorn` поднимается
без Docker. Типы колонок выбраны совместимые с обоими.

**Расхождение диалектов, о котором пришлось узнать на практике.** Встроенный `lower()`
в SQLite обрабатывает только ASCII: `lower('Анна')` возвращает строку без изменений.
Из-за этого поиск без учёта регистра по русским названиям и авторам молча не находил
ничего — тесты искали по цифровому артикулу и дефект не всплывал. PostgreSQL делает это
сам, поэтому в `app/db.py` на SQLite-подключениях регистрируется своя функция `lower`
на Python. Это единственное место, где поведение подогнано под конкретный диалект;
если таких мест станет больше, SQLite из разработки стоит убрать.

## Что сознательно отложено

- Фоновые задачи синхронизации по расписанию (E-6).
- Общий кэш расчёта или материализация рядов в таблицу (G-14): сейчас кэш у каждого
  процесса свой. Ждёт реальных объёмов (Q-9).
