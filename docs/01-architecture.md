# Архитектура

## Общая схема

```
┌───────────────┐      ┌─────────────────────────────────────────────┐      ┌──────────────┐
│  API WB       │      │                 BACKEND                      │      │  FRONTEND    │
│  (кабинеты)   │─────▶│  integrations/wb  →  models (PostgreSQL)      │◀────▶│  React + TS  │
│  ручной ввод  │      │                         ↓                     │ REST │  Vite        │
└───────────────┘      │                   calc/ (чистое ядро)         │      └──────────────┘
                       │                         ↓                     │
                       │                   api/ (FastAPI)              │
                       └─────────────────────────────────────────────┘
```

Соответствует схеме 01 из ТЗ: источники → единая база → расчётное ядро → веб-интерфейс.

## Решения и почему так

**Расчётное ядро отделено от БД.** `app/calc/` не импортирует SQLAlchemy и не знает
про HTTP. На вход — простые dataclass-структуры, на выход — результат расчёта. Это даёт
две вещи, которые прямо требует ТЗ: тест-кейсы приёмки гоняются как обычные юнит-тесты
без базы, и сверка с действующими Google Sheets делается на тех же структурах.

**Минимальная расчётная единица — пара (магазин, товар).** Один физический остаток
принадлежит ровно одной паре. Из этого автоматически следует критерий приёмки № 4:
агрегация по магазинам и по категориям — это разные группировки одного множества пар,
поэтому остаток не может попасть в итог дважды.

**Неделя — ISO-неделя строкой `2026-W46`.** Сортируется лексикографически, однозначно
отображается в понедельник, переносится в JSON без часовых поясов.

**Расчёт — на лету, не в таблице.** Хранятся только входы: базовый потенциал,
сезонность, факты, поставки, ручные правки. Всё производное считается при запросе.
Иначе «изменение прогноза → автоматический пересчёт» превращается в инвалидацию кэшей
и рассинхрон. Если упрёмся в производительность — появится материализация на уровне
сервиса, но не раньше, чем будут известны реальные объёмы (Q-9).

**Факты по неделям, а не по дням.** Вся продуктовая логика недельная. Дневная
гранулярность из WB агрегируется на входе; сырые дневные данные можно будет сложить
отдельной таблицей, когда это понадобится.

**Загрузка WB — идемпотентный upsert.** Повторный прогон того же периода не плодит
дубли: ключ `(store_id, product_id, week)`.

## Слои бэкенда

| Слой | Папка | Зависит от |
|------|-------|-----------|
| Чистое ядро | `app/calc/` | ничего, только stdlib |
| Модели и БД | `app/models.py`, `app/db.py` | SQLAlchemy |
| Сервисы | `app/services/` | модели + ядро |
| HTTP API | `app/api/` | сервисы |
| Интеграции | `app/integrations/` | модели |

Зависимости идут только вниз. `calc` ничего не импортирует из проекта.

## Хранилище

PostgreSQL в проде и в compose. Для локального старта и для тестов — SQLite:
`DATABASE_URL` по умолчанию `sqlite:///./raketa.db`, так что `uvicorn` поднимается
без Docker. Типы колонок выбраны совместимые с обоими.

**Расхождение диалектов, о котором пришлось узнать на практике.** Встроенный `lower()`
в SQLite обрабатывает только ASCII: `lower('Анна')` возвращает строку без изменений.
Из-за этого поиск без учёта регистра по русским названиям и авторам молча не находил
ничего — тесты искали по цифровому артикулу и дефект не всплывал. PostgreSQL делает это
сам, поэтому в `app/db.py` на SQLite-подключениях регистрируется своя функция `lower`
на Python. Это единственное место, где поведение подогнано под конкретный диалект;
если таких мест станет больше, SQLite из разработки стоит убрать.

## Что сознательно отложено

- Alembic-миграции — пока схема создаётся из моделей (A-6).
- Аутентификация и роли (G-1).
- Фоновые задачи синхронизации по расписанию (E-6).
- Виртуализация таблицы на тысячах SKU (F-10).
