# Развёртывание и сопровождение

README отвечает на вопрос «как поднять у себя на машине». Этот документ — про то,
как система ставится на сервер и что делать, когда она начинает вести себя не так.

Сразу о честности: всё, что здесь написано, проверено на этой сборке — но проверено
на SQLite и на одной машине. На настоящем сервере с PostgreSQL, обратным прокси
и HTTPS эта система ещё не стояла ни разу. Что именно проверено, а что рассказано
по устройству кода, сказано в конце, в разделе «Что из этого проверено».

## Из чего состоит развёрнутая система

| Часть | Чем запускается | Состояние |
|-------|-----------------|-----------|
| API | `uvicorn app.main:app` | без состояния, кроме кэша в памяти |
| Интерфейс | собранная статика `frontend/dist` | без состояния |
| База | PostgreSQL | **всё состояние системы здесь** |

Статику отдаёт обратный прокси, он же проксирует `/api` на uvicorn: приложение
статику не раздаёт, а прокси Vite работает только в разработке. Интерфейс и API
обязаны жить на одном источнике — сессионная кука поставлена с `SameSite=Lax`,
и с другого домена браузер её не отправит. Отдельный источник потребовал бы
и CORS, и защиты от CSRF; одного источника не требует ни того, ни другого.

Маршрутизации на стороне браузера нет — экраны переключаются состоянием, адрес
не меняется, поэтому прокси не нужен откат на `index.html`.

Всё это собрано в `docker-compose.prod.yml` (задача A-7) — его можно взять как
готовое развёртывание или как точное описание того, что нужно поднять руками.
`docker-compose.yml` рядом — другой файл: он поднимает только PostgreSQL
для разработки.

## Переменные окружения

Полный перечень со значениями по умолчанию — в README и в `backend/app/config.py`.
Здесь только то, что в проде обязательно задать иначе, чем по умолчанию:

| Переменная | Значение в проде | Почему |
|------------|------------------|--------|
| `DEBUG` | `false` | **Включает две проверки ниже.** По умолчанию `true` — это режим разработки |
| `SECRET_KEY` | свой случайный | Токен, подписанный общеизвестным ключом, подделывается кем угодно |
| `COOKIE_SECURE` | `true` | Иначе сессионная кука уйдёт по открытому HTTP |
| `DATABASE_URL` | `postgresql+psycopg://…` | По умолчанию файл SQLite рядом с процессом |
| `CORS_ORIGINS` | адрес интерфейса | На одном источнике не используется, но список должен быть конкретным |
| `WB_CLIENT` | `http` | По умолчанию данные берутся из фикстур репозитория |
| `WB_TOKENS` | `store01=…,store02=…` | Ключи кабинетов задаются только здесь, в базе не хранятся |

Ключу кабинета нужны **две категории** WB: «Статистика» (продажи и заказы)
и «Аналитика» (отчёт об остатках). Ключ без второй ответит на остатки 403,
и прогон будет неудачным — тогда либо выдают ключ с обеими категориями, либо
переключают остатки на прежний путь: `WB_STOCKS_SOURCE=legacy`.

Ключ генерируется так:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Переменные окружения сильнее файла `backend/.env`: файл удобен на машине
разработчика, в проде значения задаёт то, что запускает процесс (unit systemd,
переменные контейнера). Пароли и ключи в `.env` рядом с кодом не нужны.

С неправильной конфигурацией приложение не стартует и говорит, что именно не так
(проверено, тексты приведены дословно):

```
RuntimeError: SECRET_KEY не задан. Сгенерируйте ключ (...) и передайте его через окружение.
RuntimeError: COOKIE_SECURE=false вне отладки: сессионная кука уйдёт по открытому HTTP.
```

## Развёртывание с нуля

Всё — из папки `backend`, в своём окружении Python 3.11+.

**1. Зависимости.** В проде — без `-dev`: линтер и pytest на сервере не нужны.

```bash
pip install -r requirements.txt
```

**2. Схема базы.** Приложение миграции не применяет само — это явный шаг
развёртывания, иначе несколько воркеров начали бы мигрировать одновременно
(подробности — [06-migrations.md](06-migrations.md)):

```bash
alembic upgrade head
```

**3. Первый администратор.** В пустой базе администратора нет, а экран
пользователей сам требует прав администратора — войти некем. Демонстрационный
сид для этого не годится: он принесёт вместе с людьми выдуманный каталог
и выдуманные продажи. Поэтому отдельная команда:

```bash
python -m app.admin anna@example.com "Анна Петрова"
```

Пароль она либо генерирует и печатает один раз, либо берёт из переменной
`RAKETA_ADMIN_PASSWORD` — и тогда не печатает вовсе. Аргументом пароль не
передаётся намеренно: он остался бы в истории оболочки и в списке процессов.
Этой же командой возвращают доступ, если единственный администратор потерял
пароль, — она возвращает роль, включает запись и задаёт пароль заново, закрывая
прежние сессии этого человека.

**4. Интерфейс.** Из папки `frontend`:

```bash
npm ci && npm run build
```

Готовую статику из `frontend/dist` забирает прокси.

**5. Процесс API.** За прокси, на локальном адресе:

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Про число воркеров стоит знать заранее: **кэш расчёта живёт в памяти процесса.**
Четыре воркера — это четыре независимых кэша: память умножается на их число,
и каждый прогревается сам. Неверных чисел это не даёт — годность кэша решают
отметки версий в базе, — но пока неизвестны реальные объёмы (вопрос Q-9),
начинать стоит с одного-двух воркеров. Счётчик попыток входа воркеров не боится:
он лежит в базе (задача G-12). Общий кэш на все процессы есть (`CALC_CACHE_URL`,
профиль `cache` в compose), но по умолчанию выключен — на замеренных объёмах
он себя не окупает; прежде чем включать, посмотрите счётчики
`GET /api/v1/stats/calc-cache` и замеры в [08-performance.md](08-performance.md).

**6. HTTPS и прокси.** HTTPS обязателен: без него `COOKIE_SECURE=true` не даст
войти, а с `false` приложение не стартует. За прокси задайте
`TRUSTED_PROXY_HOPS` — сколько прокси стоит перед приложением (за одним
nginx это 1). Без этой настройки адрес берётся из соединения, то есть все
клиенты выглядят одним: счётчик попыток по паре «почта + адрес» вырождается,
и работает только счётчик по адресу, порог которого
(`LOGIN_MAX_ATTEMPTS_PER_ADDRESS`) тогда поднимают. Доверять заголовку без
настройки нельзя — его подставляет кто угодно.

**7. Проверка, что встало.**

```bash
curl -s https://адрес/api/v1/health
```

Ответ `{"status":"ok","version":"0.1.0"}` означает, что процесс жив и схема базы
совпала с кодом: расхождение не дало бы ему стартовать. Базу этот ответ не
опрашивает — проверка живости на каждом запросе к базе не ходит. Дальше — вход
первым администратором и любой экран: на пустой базе матрица и закупка честно
отдают ноль строк, ось недель при этом строится, а последняя закрытая неделя
считается от текущей даты.

**8. Каталог.** Заводится на вкладке **Справочники** (задача B-14), в таком
порядке: кабинет → поставщик и категория → товар → товар в кабинете. Последний
шаг — не формальность: все недельные данные привязаны к паре (магазин, товар),
и товар, не заведённый ни в один кабинет, нигде не считается. Там же задаётся
номер номенклатуры кабинета (`nmId`) — без него загрузка WB не найдёт, куда
класть продажи: незнакомый номер она складывает в `unknown_nm_ids` и проходит
мимо.

Руками заводят единицы; каталог целиком грузят файлом — кнопка **«Загрузить
номенклатуру»** там же (задача B-15). Книга Excel, строка — товар в кабинете,
колонки система ищет по названию в шапке:

```
Артикул · Название · Категория · Ниша · Поставщик · Себестоимость · Цена ·
Объём, м³ · Срок поставки, дней · MOQ · Кратность · Покрытие, недель ·
Страховой запас, недель · Кабинет · Номенклатура WB · Штрихкод · Базовый потенциал
```

Обязателен один «Артикул»; лишние колонки не читаются, порядок не важен, пустая
ячейка ничего не стирает. Готовый шаблон — кнопка «Скачать каталог» рядом:
на пустой базе это книга из одной шапки, на наполненной — весь каталог,
который можно поправить в Excel и загрузить обратно.

Файл уходит дважды: сначала разбор (в базу не пишется ничего) показывает, что
именно появится и изменится, потом тот же файл применяется. Строки с незнакомым
кабинетом или занятым номером номенклатуры отклоняются поимённо, остальные
загружаются — один кривой артикул не роняет файл. Кабинеты загрузка не заводит:
за каждым стоит ключ API, их создают руками до загрузки.

## То же самое в контейнерах

Шаги выше — что именно происходит при развёртывании. Если разворачивать
контейнерами, их выполняет `docker-compose.prod.yml`:

```bash
cp .env.prod.example .env    # заполнить SECRET_KEY и POSTGRES_PASSWORD
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml run --rm backend python -m app.admin anna@example.com "Анна Петрова"
```

Что внутри: `db` — PostgreSQL с томом для данных; `migrate` — одноразовая
служба, которая накатывает схему и завершается (бэкенд ждёт именно её успеха,
а не просто старта базы); `backend` — uvicorn без выставленного наружу порта;
`web` — nginx, который отдаёт собранный интерфейс и проксирует `/api`
на бэкенд. Наружу торчит только `web`.

Ключ подписи и пароль базы обязаны прийти из `.env`: без них compose не
поднимется и скажет, чего не хватает, — вместо того чтобы стартовать
с небезопасным значением по умолчанию.

Проверка контейнера — **живость**, а не готовность: по ней контейнер
перезапускают, и неудачная загрузка WB не должна этого вызывать.

**HTTPS в самом compose нет намеренно**: домен, сертификат и его продление —
дело машины, а не образа (вопрос Q-16). Перед этим compose ставят свой прокси
с TLS, и тогда прокси становится два — приложению нужен `TRUSTED_PROXY_HOPS=2`,
иначе адресом клиента окажется адрес внутреннего nginx. Пока HTTPS нет,
войти можно только с localhost: с `COOKIE_SECURE=true` браузер не отдаст куку
по открытому HTTP с любого другого адреса. Как это собрано на живой машине —
в разделе [«Сервер atl73.ru»](#сервер-atl73ru) ниже.

Обновление версии в такой схеме — то же, что и без контейнеров, и в том же
порядке: `docker compose -f docker-compose.prod.yml up -d --build` пересоберёт
образы, прогонит `migrate` и только потом поднимет новый бэкенд.

## Сервер atl73.ru

Единственная живая машина (задача A-10): Ubuntu 22.04, 2 ядра, 2 ГБ памяти,
30 ГБ диска, Москва. Код в `/opt/raketa`, владелец — пользователь `deploy`.
Файлы развёртывания — в [`deploy/`](../deploy/README.md).

### Как сложена цепочка

```
браузер → nginx машины (TLS, домен) → 127.0.0.1:8080 → nginx образа → backend:8000
```

Внешний nginx на машине был до нас: на нём же висит панель Portainer
на хостерском имени. Поэтому сайт «Ракеты» добавлен файлом
`/etc/nginx/conf.d/raketa.conf`, а не заменой стандартного сайта, и слушает
свои имена: `atl73.ru`, `www.atl73.ru` и адрес машины. Сделать его
`default_server` нельзя — 80-й порт уже занят сайтом хостера, 443-й панелью.

Прокси, таким образом, два, и в `.env` стоит `TRUSTED_PROXY_HOPS=2`. Это не
настройка производительности: по ней читается адрес клиента для счётчика
попыток входа (задача G-12). Поставь `1` — и адресом окажется внутренний
nginx, то есть счётчик станет общим на всех.

Порт интерфейса привязан к `127.0.0.1` (`WEB_BIND=127.0.0.1` в `.env`):
снаружи он не нужен, потому что впереди стоит nginx с TLS. **ufw намеренно
не включён**: публикация портов в Docker идёт мимо него — правило «закрыто
всё, кроме 22, 80 и 443» на опубликованный порт не действует, и `0.0.0.0:8080`
остался бы открыт из интернета при зелёном `ufw status`. Привязка к localhost
закрывает порт по-настоящему, а фаервол дал бы ложное спокойствие.

Своп на 2 ГБ добавлен: памяти 2 ГБ, а `npm ci` при сборке интерфейса
на минуту занимает почти всю.

### Настройка с нуля

Репозиторий приватный, поэтому первым делом — ключ доступа на чтение
(подробности в «Перезапуск после правок» ниже):

```bash
sudo -u deploy ssh-keygen -t ed25519 -N '' -C raketa-server-readonly \
  -f /home/deploy/.ssh/github_deploy
```

Публичную часть добавляют в настройки репозитория как Deploy key
с правом **read-only**, и только потом:

```bash
git clone git@github.com:elf-it/raketa-supply.git /opt/raketa
DOMAIN=atl73.ru SERVER_IP=<адрес> bash /opt/raketa/deploy/install.sh /tmp/actions.pub
```

`install.sh` идемпотентен: ставит nginx и certbot, создаёт самоподписанный
сертификат на время ожидания домена, пишет сайт в nginx, кладёт команды
`raketa-deploy` и `raketa-cert`, включает таймер ожидания домена и записывает
ключ GitHub Actions с принудительной командой. `.env` он не создаёт
намеренно — в нём пароль базы и ключ подписи сессий.

Дальше `.env` заполняется руками. Значения, отличающиеся от образца:

```ini
WEB_BIND=127.0.0.1
TRUSTED_PROXY_HOPS=2
CORS_ORIGINS=https://atl73.ru
COOKIE_SECURE=true
```

и первый запуск: `sudo -u deploy raketa-deploy`.

### Что сейчас в базе

Демонстрационные данные — тот же набор, что даёт `python -m app.seed` локально:
3 кабинета, 12 товаров, 18 пар, 360 недельных фактов и столько же планов,
11 поставок, 17 записей журнала правок, история на 20 недель назад.

Данные **статичные**: ключей кабинетов WB нет (задача E-3), `WB_TOKENS` пуст,
и загрузка из WB на этой машине завершится ошибкой — это не поломка, а
отсутствие ключей. Расписание загрузки поэтому не ставилось.

Из этого следует, что **свежесть загрузки протухает сама**: `SYNC_STALE_HOURS`
равен 36 часам, и через полтора дня готовность становится `degraded`
(`sync: stale`). Это правда, а не поломка. Порог поднимать не стоит — он
замолчит и тогда, когда данные протухнут по-настоящему. Перед показом данные
перезаливают:

```bash
cd /opt/raketa && sudo -u deploy docker compose -f docker-compose.prod.yml run --rm \
  -v /opt/raketa/deploy/refresh-demo.py:/tmp/refresh.py backend \
  python -c 'import runpy; runpy.run_path("/tmp/refresh.py")'
```

**Не `python -m app.seed` напрямую.** Сид задуман для пустой базы и чистит
таблицу пользователей вместе с остальными: все выданные пароли перестали бы
работать без предупреждения, а своего администратора пришлось бы заводить
заново. `deploy/refresh-demo.py` снимает учётные записи до сида и возвращает
после — с хешами паролей, ролями и отметкой смены пароля. Сессии при этом
закрываются (строки создаются заново, номера другие): войти нужно ещё раз,
прежним паролем.

**Пароли демонстрационных учётных записей на сервере заменены на случайные.**
В репозитории они лежат открыто (`backend/app/seed.py`), а сайт открыт
в интернете: оставить их значило бы отдать вход администратора любому, кто
прочитал репозиторий. Учётки и роли при этом те же. Новые пароли знает тот,
кто разворачивал; сменить их заново — экран пользователей или
`PUT /api/v1/auth/users/{id}`.

Свой администратор (`app.admin`) заведён отдельно: сид чистит таблицу
пользователей, поэтому его создают **после** заливки данных, а не до.

### Перезапуск после правок

Автоматически: таймер `raketa-watch` раз в две минуты сравнивает развёрнутый
коммит с указателем `ci-green` и, если тот ушёл вперёд, запускает
`raketa-deploy`. То есть push в `main` доезжает на сервер сам, через время
прогона CI плюс до двух минут.

**`ci-green` — это не ветка для людей**, а метка «этот коммит проверен»:
её переставляет сам CI после обеих проверок (`.github/workflows/ci.yml`,
задача A-11). Выкладывается именно она, а не вершина `main`: на `main` может
лежать правка, о которой уже известно, что она сломана. Пока проверки идут,
указатель стоит на прежнем коммите, и тик ничего не делает. Перезапуск CI
на старом коммите сдвинет метку назад, и сервер честно откатится — выложено
ровно то, что последним признали проверенным.

Прежде сторож спрашивал состояние проверок у публичного API GitHub. После
перевода репозитория в приватный (задача A-11) такой запрос требует токена —
то есть ещё одного секрета на машине и ещё одного срока его действия.
Указатель лежит в самом репозитории и читается тем же ключом, которым сервер
и так забирает код: ни API, ни токена, ни предела запросов.

**Спрашивает сервер, а не GitHub стучится на сервер.** Обратный способ
(рабочий процесс Actions ходит по ssh) быстрее на эти две минуты, но требует
приватного ключа в секретах репозитория, а секреты читает всякий, кто может
менять рабочие процессы. При опросе наружу не открыто ничего.

**Доступ к приватному репозиторию — ключ развёртывания только на чтение.**
Приватная часть лежит у пользователя `deploy` (`~/.ssh/github_deploy`)
и создана на самой машине: она никуда не уезжала и в репозитории её нет.
В GitHub добавлена только публичная часть, в настройках репозитория, как
Deploy key с правом read-only — не токен учётной записи: ключ действует
на один репозиторий, ничего не может записать и отзывается одной кнопкой.
Ключ хоста `github.com` записан после сверки с опубликованным отпечатком,
а не принят на доверие при первом подключении.

Если доступ отвалится (ключ отозвали, GitHub недоступен), `ls-remote`
вернёт пустоту, и сторож скажет об этом в журнал: «нет отметки проверенного».
Молчать здесь нельзя — иначе сервер «работает», а правки не едут.

Быстрый путь оставлен **включаемым**: `.github/workflows/deploy.yml`, четыре
секрета (`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`)
и переменная репозитория `DEPLOY_ENABLED=true`. Без переменной задание
пропускается, а не падает: красный крест на каждом push означал бы «что-то
сломано», когда ничего не сломано. После включения таймер на сервере можно
погасить — `systemctl disable --now raketa-watch.timer`; оставить оба тоже
можно, второй увидит, что выкладывать нечего.

Руками то же самое: `sudo -u deploy raketa-deploy` на сервере — он тоже
возьмёт проверенный коммит. Выложить что-то другое (например вершину `main`,
не дождавшись CI): `sudo -u deploy DEPLOY_BRANCH=main raketa-deploy`.
Посмотреть, что делает слежение: `journalctl -u raketa-watch -n 20`.

Что делает `raketa-deploy`: берёт блокировку (два `up --build` на двух ядрах —
это не быстрее, а OOM), `git reset --hard` на проверенный коммит (сервер руками
не правят, слияние на боевой машине кончается конфликтом в три часа ночи),
пересборка и запуск, ожидание ответа `/api/v1/health` через весь путь.
**Если приложение не ответило — откат на прежний коммит и пересборка его.**
Выкладка, оставившая сайт лежать, хуже невыложенной правки.

Последним делом прогон обновляет установленные копии `raketa-deploy`
и `raketa-watch` — **записью в существующий файл, а не заменой файла**.
`install` и `cp` сначала снимают прежний, а для этого нужно право записи
в `/usr/local/bin`, которого у `deploy` нет и быть не должно: владеть файлом
мало. Именно на этом обновление копий молча не работало, а `set -e` ронял
прогон уже после удачной выкладки. Копию `raketa-cert` прогон не трогает:
её systemd запускает от root, и право на push не должно становиться правом
на root — её обновляет `install.sh`.

Секреты репозитория для включаемого быстрого пути: `DEPLOY_HOST`,
`DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`. Ни адреса, ни
пользователя в файлах репозитория нет — он хоть и приватный, но секреты
читает всякий, кто может менять рабочие процессы, а это шире, чем нужно.
Ключ записан на сервере с принудительной командой: им нельзя сделать ничего,
кроме развёртывания.

**Приватный репозиторий расходует минуты GitHub Actions** из квоты учётной
записи (на бесплатном тарифе 2000 минут в месяц), тогда как публичный
не расходовал. Прогон CI — около трёх минут, то есть запас на несколько
сотен push в месяц; но если минуты кончатся, CI встанет, метка `ci-green`
перестанет двигаться, и выкладка остановится — молча для сайта, но заметно
в журнале сторожа: «правок нет» при наличии правок.

### Сертификат

**Состояние:** выдан 18 ноября 2026 на `atl73.ru` и `www.atl73.ru`
(Let's Encrypt, до 16 февраля 2027), HSTS включён, продление отрепетировано
`certbot renew --dry-run`. Свой таймер `raketa-cert` выключился сам — дальше
продлевает штатный `certbot.timer`, а хук перезагружает nginx.

Как механизм устроен (нужно при переносе на другую машину):

`raketa-cert` (таймер systemd, раз в час) сам проверяет A-запись и выдаёт
сертификат, **как только домен укажет на эту машину**. Пока запись смотрит
в другое место, сертификат не запрашивается: проверка владения от
Let's Encrypt ушла бы на чужую машину, а несколько таких провалов подряд
наказываются запретом на неделю. Поэтому неподходящая A-запись здесь —
не ошибка, а причина подождать до следующего срабатывания.

До настоящего сертификата сайт работает по самоподписанному: браузер
показывает предупреждение, а вход работает — без HTTPS приложение вне отладки
не стартует вовсе. HSTS включается вместе с настоящим сертификатом и не
раньше: этот заголовок запрещает браузеру «пройти всё равно» и с
самоподписанным закрыл бы сайт насовсем.

После выдачи `raketa-cert` переставляет ссылку `/etc/raketa/cert`
на `/etc/letsencrypt/live/atl73.ru`, пишет HSTS, перезапускает nginx, ставит
хук перезагрузки nginx на продление (иначе nginx держал бы открытым старый
файл и отдавал просроченный сертификат) и выключает свой таймер: дальше
работает штатный `certbot.timer`.

**Проверять A-запись нужно у тех серверов, которым домен делегирован сейчас,
а не у тех, что помнишь.** На этом домене смена адреса шла вместе со сменой
самих NS: делегирование переехало с `nic.ru` на `spaceweb`, а серверы `nic.ru`
остались доступны и продолжали отдавать прежний адрес — на вид «запись
не поменялась». Правильный порядок: `dig +short NS atl73.ru` (или
`dig +trace`), и только потом спрашивать полученные серверы. Пока
делегирование доходит до разных разрешителей (у `.ru` это сутки), часть
интернета ещё получает старый адрес; поправить это нельзя, можно только
переждать — или, если доступ к прежней зоне остался, поставить тот же адрес
и в ней, чтобы оба ответа совпадали.

Регистрация в Let's Encrypt **без адреса почты**: письма об истечении
не придут. Продлением занимается таймер, а адрес ушёл бы во внешнюю службу —
кто хочет предупреждений, вписывает свой в `ACME_EMAIL` в
`/etc/systemd/system/raketa-cert.service`.

### Чего в этой схеме нет

* **Второй машины.** Выкладка — это пересборка на той же машине: минуту-две
  сайт отвечает старой версией, затем новой. Переключения без разрыва нет.
* **Сборки образов в CI.** Собирает сервер. На одной машине хранилище
  образов — лишний узел; на второй машине это пришлось бы переделать.
* **Копий вне этой машины.** Суточные копии с проверкой восстановления есть
  (задача G-21), но лежат они рядом с базой: потеря машины забирает и то,
  и другое. Куда увозить — решение владельца данных, место оставлено
  (`BACKUP_SYNC_CMD`).
* **Проверки, что выложилось именно то.** `raketa-deploy` проверяет, что
  приложение отвечает, а не что числа на экране верны.

## Обновление версии

Порядок — миграции, потом новый код:

```bash
git pull && pip install -r requirements.txt
alembic upgrade head
# перезапуск процесса API
```

Между этими шагами на новой схеме работает старый код. Добавление таблиц
и колонок он переживает, переименование и удаление — нет, поэтому обновление
с такой ревизией делается в окно обслуживания. Какая ревизия что меняет, видно
в `backend/alembic/versions/`: заголовок каждой подписан задачей.

Откат — обратный: сначала старый код, потом `alembic downgrade -1`. Данные
удалённых колонок `downgrade` не возвращает: он возвращает схему, а не историю.

После перезапуска первый запрос считает всё заново — кэш расчёта пустой. На
замеренных объёмах это 0,88 с вместо 0,14 с на матрицу ([08-performance.md](08-performance.md)).

## Регулярные работы

**Загрузка данных WB.** По расписанию — командой, из папки `backend`:

```bash
python -m app.sync --days 14
```

Токен ей не нужен: она ходит в базу напрямую, тем же кодом, что и кнопка
на экране. Расписание держит тот, кто запускает процесс, — приложение своего
планировщика не имеет намеренно: фоновый поток внутри него на нескольких
воркерах дал бы столько же одновременных загрузок, сколько воркеров.

Код возврата говорит планировщику, что случилось: `0` — загрузилось,
`1` — хотя бы один кабинет упал, `2` — предыдущая загрузка ещё идёт. Две
загрузки разом не начинаются; прогон, чей процесс убили, узнаётся по возрасту
(`--lock-minutes`, по умолчанию 30) и расписание не останавливает.

Ежедневному прогону хватает `--days 14`: глубже имеет смысл раз в неделю или
после простоя. Как часто грузить на самом деле — вопрос Q-17.

В конце прогона команда отправляет алерты настроенными каналами (раздел
«Алерты»): об упавшем кабинете дежурный узнаёт сразу, а не из следующего
прогона. Недоставленный алерт на код возврата загрузки не влияет —
планировщику важно, загрузились ли данные.

**cron** (каждый день в 5 утра; письмо придёт, только если команда вернёт не ноль):

```bash
0 5 * * * cd /opt/raketa/backend && /opt/raketa/.venv/bin/python -m app.sync --days 14
```

**systemd timer** — то же самое, если cron в системе не живёт: `OnCalendar=*-*-* 05:00:00`
и `Type=oneshot` с той же командой; `systemctl status raketa-sync` покажет код
последнего прогона.

**Планировщик заданий Windows** — действие «Запуск программы»:

```bash
schtasks /create /tn "Ракета · загрузка WB" /tr "C:\raketa\backend\.venv\Scripts\python.exe -m app.sync --days 14" /sc daily /st 05:00
```

Повторный запуск безопасен: факты пишутся upsert-ом по тройке (магазин, товар,
неделя), двойного учёта не будет. Человек может в любой момент запустить
загрузку кнопкой на экране — это та же работа.

**Сколько это длится.** У метода «Продажи» лимит WB — 1 запрос в минуту
на профиль продавца, а в одном ответе условно не больше 80 000 строк. Поэтому
глубокая загрузка идёт страницами с паузой: при `WB_MAX_PAGES=20` кабинет
занимает до 20 минут, то есть укладывается в получас, после которого прогон
считается брошенным (`--lock-minutes`). Если данные кончились позже страниц,
прогон помечается **неудачным** — записанные факты верны, но картина неполная,
и выглядеть полной она не должна. В таком случае поднимают `WB_MAX_PAGES`
(и `--lock-minutes` вместе с ним) или грузят меньшую глубину.

**Закрытие недели.** `POST /api/v1/forecast/close-week` фиксирует прогноз недели
как её план — дальше он не пересчитывается. Делает человек, когда факт недели
загружен; автоматического закрытия нет намеренно: решение, что неделя закончена,
принимает тот, кто отвечает за цифры.

**Чистка журналов.** Две таблицы растут без предела: `sync_runs` — строка
на каждый прогон каждого кабинета, `adjustment_log` — строка на каждую
правленную ячейку (одна массовая правка доходит до 20 000). Счётчик попыток
входа и несопоставленные номера убирают за собой сами, эти — нет. Та же
команда убирает просроченные отзывы сессий (G-20) — им срока хранения
не назначают, см. ниже.

```bash
python -m app.cleanup --dry-run      # показать, что удалится
python -m app.cleanup                # прогоны старше 90 дней
```

Раз в неделю этого достаточно; ставится тем же планировщиком, что и загрузка.
Сначала всегда `--dry-run`: удаление в базе не отменяется кнопкой.

**Последний завершённый прогон каждого кабинета не удаляется никогда** —
по нему считается свежесть данных, и без него кабинет выглядит «ни разу
не загружался», а алерт о протухших числах замолкает. Команда говорит,
у каких кабинетов она эту строку сберегла.

**Журнал корректировок по умолчанию не чистится.** Это доказательство: кто
поставил число и когда. Срок хранения ему назначает тот, кто отвечает за
данные, поэтому нужен отдельный ключ: `--journal-days 365`.

**Отозванные сессии чистятся всегда и без ключа.** Строка об отзыве (задача
G-20) появляется на каждый выход и нужна ровно до `exp` своего токена: после
него токен отвергает подпись. Держать дольше бессмысленно, удалять раньше —
значит вернуть отозванный токен в работу, так что выбирать здесь нечего
и настройки нет. Команда говорит, сколько таких строк убрала.

**Резервные копии** (задача G-21). Всё состояние — в базе, поэтому копия это
`pg_dump`. На сервере это делает таймер:

```bash
sudo -u deploy raketa-backup          # сделать копию сейчас
systemctl list-timers raketa-backup   # когда следующая
journalctl -u raketa-backup -n 30     # что было в прошлый раз
cat /var/backups/raketa/last-status    # ok или СБОЙ, одной строкой
```

Регламент, записанный числами:

| Что | Решение | Почему так |
| --- | --- | --- |
| как часто | раз в сутки, 03:30 MSK | окно потери данных — до суток; меньше требует журналирования WAL, а это уже другой механизм |
| на какую глубину | 14 копий | двух недель хватает, чтобы заметить порчу, которую никто не видел неделю |
| где лежат | `/var/backups/raketa`, права 0700 | в них вся база целиком, читать их может только владелец |
| пропущенный прогон | делается после загрузки (`Persistent=true`) | иначе каждый простой машины оставлял бы сутки без копии |

**Каждая копия тут же разворачивается и сверяется.** Прогон создаёт отдельную
базу, восстанавливает в неё снимок, сверяет ревизию схемы с живой базой
и убеждается, что ключевые таблицы не пусты, после чего базу удаляет. Копия,
которую ни разу не разворачивали, — это предположение о копии; файл
правильного размера, который не восстанавливается, хуже отсутствия файла,
потому что создаёт уверенность. Расхождение числа строк со живой базой
не считается сбоем (между снимком и сверкой кто-то мог записать), но пишется
в журнал.

Снимок делает **сам контейнер базы**: `pg_dump` той же версии, что сервер.
Снимок, сделанный клиентом другой версии, восстанавливается не всегда,
и узнают об этом в худший день.

Неудачный прогон **удаляет недоделанный файл** и пишет `СБОЙ` в
`last-status`: обрубок в каталоге копий опаснее пустого каталога.

**Чего эти копии не закрывают.** Они лежат на той же машине, что и база.
Потеря диска или VPS забирает и то, и другое — это не защита от утраты
машины, а защита от порчи данных, ошибочного удаления и неудачной миграции.
Куда увозить копии наружу — решение с чужим адресом и чужими ключами, его
принимает владелец данных (вопрос Q-16). Место для этого оставлено: переменная
`BACKUP_SYNC_CMD` в `/etc/systemd/system/raketa-backup.service` получает путь
к свежему файлу в `BACKUP_FILE` и может быть чем угодно — `rsync`, `rclone`,
`aws s3 cp`. Пока она пуста, скрипт говорит об этом в каждом прогоне.

**О сбое копии никто не узнает сам.** Канал алертов на этой машине не настроен
(`SMTP_HOST` и `ALERT_WEBHOOK_URL` пусты), поэтому неудача видна только
в `journalctl` и в `last-status`. Правильный способ — тот же, что для системы
целиком (задача G-18): `BACKUP_HEARTBEAT_URL` получает пинг **только после
удачного прогона**, и сторож снаружи шумит, когда пинг пропал. О собственном
молчании скрипт сообщить не может.

**Восстановление из копии** — то, что стоит проделать руками хотя бы раз,
не дожидаясь повода:

```bash
cd /opt/raketa
C="docker compose -f docker-compose.prod.yml"
# 1. остановить приложение, чтобы оно не писало в базу во время восстановления
sudo -u deploy $C stop backend web
# 2. развернуть копию в новую базу и переключиться на неё — так прежняя
#    остаётся на месте, и ошибка восстановления ничего не стоит
sudo -u deploy $C exec -T db psql -U raketa -d postgres \
  -c 'create database raketa_restored'
sudo -u deploy $C exec -T db pg_restore -U raketa -d raketa_restored --no-owner \
  < /var/backups/raketa/raketa-20261120-0330.dump
# 3. проверить глазами, что это те данные
sudo -u deploy $C exec -T db psql -U raketa -d raketa_restored \
  -c 'select count(*) from week_facts' -c 'select version_num from alembic_version'
# 4. переименовать: приложение ходит в базу по имени из .env
sudo -u deploy $C exec -T db psql -U raketa -d postgres \
  -c 'alter database raketa rename to raketa_before_restore' \
  -c 'alter database raketa_restored rename to raketa'
sudo -u deploy $C start backend web
```

Старую базу (`raketa_before_restore`) удаляют только после того, как
убедились в восстановленной: `drop database raketa_before_restore`.

**Сколько воркеров и какой предел кэша.** По замерам (`docs/08-performance.md`,
раздел «Нагрузка на объёмах»): воркеров — не меньше, чем людей, работающих
одновременно, иначе запросы отнимают время друг у друга и общая пропускная
способность падает. `CALC_CACHE_ENTRIES` — не меньше, чем позиций × 2
(матрица и закупка считают по разным осям недель); с меньшим пределом кэш
вытесняет то, что сам же положил, и экран отвечает вчетверо медленнее.
Система скажет об этом сама строкой «кэш расчёта не вмещает каталог».
Проверить на своих объёмах: `python -m app.bench --users 5 --seconds 20`
(читает, ничего не меняет).

**На что смотреть глазами.** Журнал синхронизаций `GET /api/v1/sync/runs` — статус
и текст ошибки по каждому прогону. Журнал корректировок на экране — кто и что
правил в прогнозе. О неудачной загрузке не нужно догадываться: она видна плашкой
на экране и готовностью (ниже).

## Логи и мониторинг

**Логи** пишутся в stdout — одной строкой на запрос:

```
2026-11-15 11:43:54 INFO    raketa req=8be8d60 user=2/editor POST /api/v1/sync/wb status=200 ms=107
2026-11-15 11:43:54 INFO    raketa req=8be8d60 user=-        кабинет загружен store=store01 facts=96 unknown=0
```

Номер запроса (`req=`) связывает строки одного запроса между собой и уезжает
в заголовке `X-Request-Id`: по нему человек, увидевший ошибку на экране, находит
свой запрос в логе. Если номер ставит прокси, он сохраняется. События внутри
обработчика выходят с `user=-` — отметка о человеке туда не доезжает, но номер
у строк общий, и в строке самого запроса он есть.

`LOG_LEVEL` задаёт уровень, `LOG_FORMAT=json` — строку-объект на событие для
сборщика логов. Что именно собирает логи, зависит от схемы развёртывания
(вопрос Q-16); ротация и хранение — на стороне того, кто запускает процесс.

**В лог не попадают** пароли, токены, куки, строка запроса (в ней поисковые
запросы и фильтры) и почта: неудачный вход пишется с маской `a***@company.ru`.

**Мониторингу** нужны две ручки, и путать их дорого:

| Ручка | Что отвечает | Чем мерить |
|-------|--------------|------------|
| `GET /api/v1/health` | процесс жив | перезапуск зависшего процесса |
| `GET /api/v1/health/ready` | системе можно верить | алерт дежурному |

Готовность отвечает **503**, если база не отвечает или данные кабинета отстали:
последний прогон упал либо удачный был раньше, чем `SYNC_STALE_HOURS` назад
(по умолчанию 36 ч). Кабинет, который ни разу не загружался, нездоровьем
не считается — иначе на свежем развёртывании алерт горел бы до первой загрузки.
Обе ручки открыты без входа и не раскрывают ни названий кабинетов, ни чисел;
подробности с названиями отдаёт `GET /api/v1/sync/status`, и она закрыта ролью.

Минимальный мониторинг — любая проверка, умеющая дёргать URL раз в несколько
минут и ругаться на код ответа:

```bash
curl -fsS https://адрес/api/v1/health/ready > /dev/null || echo "Ракета: данные устарели"
```

Человеку в интерфейсе о том же говорит плашка над таблицей.

## Алерты: как система сообщает о себе сама

Готовность и плашка отвечают тому, кто спросил. Алерты — наоборот: система
пишет сама, в почту или мессенджер. Доставка необязательная: без настроек
система ведёт себя в точности как до задачи G-16.

| Переменная | Что это |
|------------|---------|
| `SMTP_HOST`, `SMTP_PORT` | почтовый сервер; порт по умолчанию — по режиму (587 / 465 / 25) |
| `SMTP_SECURITY` | `starttls` (по умолчанию), `ssl` или `none` |
| `SMTP_USER`, `SMTP_PASSWORD` | вход на сервер, если он нужен |
| `ALERT_EMAIL_FROM` | обратный адрес; без него письмо отбрасывают молча |
| `ALERT_EMAIL_TO` | получатели через запятую |
| `ALERT_WEBHOOK_URL` | входящий вебхук мессенджера — **это секрет** |
| `ALERT_WEBHOOK_CHAT_ID` | только для Telegram: номер чата |
| `ALERT_REPEAT_HOURS` | через сколько часов напоминать о неисправленном сбое (0 — не напоминать) |
| `ALERT_SUBJECT_PREFIX` | приставка темы, по умолчанию `[Ракета]` |
| `HEARTBEAT_URL` | пульс наружу — **это секрет**; раздел «Сторож снаружи» |

В тело вебхука уходит `{"text": "…"}` — его понимают входящие вебхуки Slack
и Mattermost; с `ALERT_WEBHOOK_CHAT_ID` рядом с текстом едет `chat_id`, и это
`sendMessage` Telegram. Для другого мессенджера нужна либо такая же ручка,
либо переходник в одну строку.

**Полунастроенная доставка — отказ старта.** `SMTP_HOST` без получателей или
получатели без сервера выглядят как настроенные алерты, а ведут себя как их
отсутствие: о сбое никто не узнает, но все уверены, что узнают. Приложение
в таком случае не стартует и говорит, чего не хватает.

**Проверить канал** — до того, как он понадобится:

```bash
python -m app.alerts --test
```

Команда отправляет проверочное сообщение во все настроенные каналы и говорит,
кто принял; код возврата 1 — не принял никто. Канал, в который ни разу
не отправляли, — это предположение о канале: пароль приложения, закрытый порт,
вебхук, отозванный полгода назад.

**Кто отправляет.** Загрузка сообщает о себе сама: `python -m app.sync` в конце
прогона отправляет то, что нужно отправить. Отдельный прогон нужен для случая,
когда загрузка не запускалась вовсе, — его ставят в расписание чаще загрузки:

```bash
*/15 * * * * cd /opt/raketa/backend && /opt/raketa/.venv/bin/python -m app.alerts
```

Частый прогон потоком сообщений не грозит: об одном и том же поводе сообщается
один раз, а напоминание уходит не чаще `ALERT_REPEAT_HOURS`. `--dry-run`
показывает, что ушло бы, и ничего не отправляет.

**О чём приходит сообщение.** Упавшая загрузка кабинета, отставшие данные
(порог — тот же `SYNC_STALE_HOURS`) и восстановление: иначе дежурный, получивший
«упала», не узнает, что всё прошло. Кабинет, который ни разу не загружался,
поводом не считается — как и в готовности. В сообщении есть название кабинета
и текст ошибки из журнала прогона: алерт уходит известному получателю, и без
названия он бесполезен. Похожее на ключ (JWT кабинета WB) из текста вычищается,
адрес вебхука не выводится ни в лог, ни в вывод команд.

**Чего алерты не умеют и не могут.** Сообщить о себе система может, только пока
её процессы живы: выключенная машина, мёртвый планировщик или недоступная база
означают, что отправлять некому и нечем — состояние отправленных алертов лежит
в той же базе. Это предел любого алерта изнутри, а не недоделка: о собственной
смерти сообщить нельзя. Закрывается он снаружи — следующим разделом.

## Сторож снаружи: пульс и опрос готовности

Нужны оба сигнала, и они ловят разное:

| Сигнал | Кто кого спрашивает | Что ловит |
|--------|---------------------|-----------|
| **Пульс** (`HEARTBEAT_URL`) | система дёргает сторожа | машина выключена, планировщик мёртв, база недоступна — словом, система молчит |
| **Готовность** (`/health/ready`) | сторож спрашивает систему | система жива, но данные протухли или база не отвечает |

**Пульс.** После удачного прогона `python -m app.alerts` дёргает адрес
из `HEARTBEAT_URL`. Сторож снаружи ждёт этот сигнал и поднимает тревогу, когда
он пропал. О собственной смерти сообщить нельзя — но можно делать обратное,
пока жив, и тогда **молчание само становится сообщением**. Если прогон
неудачный (алерт не доставлен, база недоступна), пульса нет намеренно.

Адрес даёт сторож. Подойдёт любой, кто принимает GET:

```bash
# healthchecks.io — бесплатный тариф, свой ключ в адресе
HEARTBEAT_URL=https://hc-ping.com/<ключ>
# Uptime Kuma, проверка типа Push
HEARTBEAT_URL=https://kuma.ваш-домен/api/push/<ключ>
# Dead Man's Snitch
HEARTBEAT_URL=https://nosnch.in/<ключ>
```

Срок молчания у сторожа ставят вдвое больше периода расписания: прогон раз
в 15 минут — тревога через полчаса. Один пропущенный прогон тогда не будит
дежурного, а два подряд — будят. Адрес пульса секретен (в нём ключ), и наружу
система его не печатает: в логе и в выводе команд он маскируется.

Проверить связь целиком — каналы доставки и пульс:

```bash
python -m app.alerts --test
```

**Опрос готовности.** Если ставить сторожа негде, хватит соседней машины
с cron: проверка, умеющая дёрнуть URL и посмотреть код ответа, — это любая
проверка.

```bash
*/5 * * * * curl -fsS https://адрес/api/v1/health/ready > /dev/null || echo "Ракета: не готова" | mail -s "Ракета" дежурный@почта
```

**Чего не ловит ни то, ни другое.** Сторож на той же машине бесполезен: он
умрёт вместе с системой. Пульс и опрос должны идти с другой машины или
из чужого сервиса — иначе это снова алерт изнутри, только с лишними шагами.

## Что делать, когда

**Приложение не стартует.** Четыре сообщения, и все четыре говорят, что делать:
две проверки конфигурации (`SECRET_KEY`, `COOKIE_SECURE`, см. выше) и две
проверки схемы — «База не инициализирована: нет таблицы alembic_version» и «Схема
базы устарела: ревизия X, ожидается Y». На устаревшей базе приложение работать
отказывается намеренно: работать на ней хуже, чем не запуститься.

**Синхронизация упала.** Это видно, не заходя в журнал: готовность отвечает 503,
а в интерфейсе над таблицей появляется плашка с названием кабинета и текстом
ошибки. Статус и текст по каждому прогону — в `GET /api/v1/sync/runs`, а причина
падения с трассировкой — в логе, по номеру запроса. Прогон можно просто
перезапустить (он идемпотентен).

**Кабинет что-то продаёт, а в системе этого нет.** Непустой `unknown_nm_ids`
в ответе загрузки — не сбой, а несопоставленная номенклатура: номера, которых
нет ни на одной паре, и продажи по ним не считаются нигде. Список — на вкладке
**Справочники → Сопоставление**, с кабинетом и числом прогонов, в которых номер
встретился; там же он привязывается к товару. Факты по привязанному номеру
приедут следующей загрузкой: задним числом система их не перезапрашивает.

**Одна позиция выглядит как две.** Товар, заведённый дважды, делит спрос
и закупку пополам. Кандидаты на слияние — там же, в «Сопоставлении»: система
показывает похожих по штрихкоду, названию и артикулу, а решает человек.
Слияние переносит кабинеты вместе с их прошлым; если обе позиции заведены
в одном кабинете, оно отказывает — это не дубль.

**Человек не может войти.** Три причины, различимые по ответу:

- `429` — сработал счётчик попыток. Ждать четверть часа: счётчик лежит в базе
  и перезапуском не обнуляется (задача G-12). Если ждать нельзя, записи
  о попытках этого человека убирают из таблицы `login_attempts`.
- `401` при верном пароле — запись отключена администратором либо пароль сменили
  и прежняя сессия закрыта.
- Забытый пароль — администратор задаёт новый на экране пользователей. Сброса по
  почте нет и не будет без почтового сервиса. Если забыл единственный
  администратор — `python -m app.admin` с его почтой.

**«Цифры не те».** Порядок разбора: сначала журнал корректировок — ручная правка
держится приоритетом над формулой, и чаще всего «не те» цифры поставил человек.
Потом — потенциал и сезонность: их правка меняет расчёт всей выборки.
На кэш расчёта подозрение проверяется прямо: `CALC_CACHE_ENTRIES=0` выключает его
совсем, расчёт идёт на каждый запрос. Если числа те же — кэш не при чём.
Он и не должен быть при чём: годность записи решают отметки версий в базе,
поэтому правка через один воркер обесценивает кэш у остальных.

**Медленно.** Сначала — холодный ли кэш (сразу после перезапуска первый запрос
считает всё). Предел кэша меньше каталога бесполезен: запрос обходит все пары
подряд и вытесняет то, что сам же положил, — `CALC_CACHE_ENTRIES` держат не ниже
двух записей на пару. Замеры и разбор, что сколько стоит, —
в [08-performance.md](08-performance.md).

**Растёт база.** Растут недельные факты (по строке на пару и неделю), журнал
корректировок и журнал синхронизаций. Чистки или архивации нет: данных такого
объёма, чтобы это стало проблемой, в системе пока не бывало, а удалять журнал
правок без спроса нельзя — он подписан авторами.

## Чего в сопровождении нет

Это не оговорки, а то, что придётся сделать до настоящей эксплуатации:

- **Самого сторожа снаружи** — его заводит тот, кто держит сервер (вопрос Q-16).
  Со стороны системы всё готово: она отправляет алерты и шлёт пульс
  (раздел «Сторож снаружи»), но ждать этот пульс и шуметь при его пропаже
  должен кто-то, кто живёт не на той же машине.
- **Чтения карточек товаров из кабинетов WB** — вопрос Q-15. Номенклатура
  заводится руками или файлом (шаг 8); номер `nmId` человек приносит сам.
- **HTTPS в боевой сборке** — сертификаты и домен добавляет тот, кто
  разворачивает (вопрос Q-16); `docker-compose.prod.yml` заканчивается на nginx
  без TLS.
- **Своего расписания внутри системы** — вопрос Q-17. График держит внешний
  планировщик (раздел «Регулярные работы»); задать его в интерфейсе нельзя.
- **Регламента и проверки резервных копий** — вопрос Q-16.
- **Отправки заказа поставщику** — заказ выгружается в XLSX, отправляет человек.

## Что из этого проверено

**Боевая сборка в контейнерах** — целиком, на этой машине: образы собраны,
`docker compose -f docker-compose.prod.yml up` поднял PostgreSQL, прогнал
миграции отдельной службой, запустил бэкенд и nginx. Через nginx ответили
живость и готовность (на пустой базе она зелёная), первый администратор заведён
командой в контейнере, вход и экраны работают, логи пишутся строкой-объектом,
номер запроса в них — тот, что выдал nginx. После проверки всё остановлено,
тома удалены.

Остальное — на чистой базе SQLite, запуском ровно тех команд, что приведены
выше: `alembic upgrade head` (шесть ревизий), `python -m app.admin` (создан
администратор, пароль из переменной в вывод не попал), вход этим администратором
через обычную ручку входа, пустая матрица и пустая закупка (ноль строк, ось
недель построена, последняя закрытая неделя посчитана от даты), а также оба
отказа старта — без `SECRET_KEY` и с `COOKIE_SECURE=false` вне отладки.
Команда первого администратора закрыта тестами (`backend/tests/test_admin_cli.py`),
включая то, что восстановление доступа гасит прежние сессии.

**Доставка алертов** проверена живьём на этой машине, не только тестами:
поднимались настоящий SMTP-приёмник и приёмник вебхука, и через них прошёл весь
путь — проверка каналов (`--test`), сообщение об упавшей загрузке, молчание
на втором прогоне, сообщение о восстановлении, которое отправила сама
`python -m app.sync`, и отказ обоих каналов (код возврата 1, отметка
об отправке не поставлена). Письмо пришло с темой и текстом, вебхук — с тем же
текстом в `{"text": …}`; ключ кабинета из текста ошибки ушёл замаскированным.
Этой проверкой нашлась и закрыта дыра: HTTP-клиент сам писал в лог полный адрес
вебхука, то есть его ключ. Настоящие почтовые сервисы (аутентификация, TLS,
SPF/DKIM) и настоящие мессенджеры не проверялись — для этого нужны их адреса
и ключи, то есть ответ на вопрос Q-16.

**Пульс наружу** проверен так же — подставным сторожем, который ведёт себя как
healthchecks.io: два прогона отдали пульс, после чего команда замолчала,
и сторож поднял тревогу через свой срок молчания. Проверено и обратное: после
неудачного прогона пульс не уходит, а адрес с ключом не попадает ни в вывод,
ни в лог. Настоящий сторож (healthchecks.io, Uptime Kuma) не подключался:
нужен его адрес — снова вопрос Q-16.

Не проверено ничем: HTTPS и настоящий домен, несколько воркеров, `pg_dump`
и восстановление из копии, загрузка WB по реальным ключам (вопрос Q-3),
и вся система на сервере, а не на одной машине.
