# Ракета · Веб-система снабжения

Прогнозирование продаж, остатки и планирование закупок для магазинов Wildberries —
замена расчётов, которые сейчас живут в Google Sheets.

Реализация по ТЗ v0.5 от 09.11.2026. Расшифровка исходного ТЗ, включая блок-схемы
и макеты, — в [docs/00-tz-source.md](docs/00-tz-source.md). Рабочий список задач —
[BACKLOG.md](BACKLOG.md).

## Что уже работает

- **Единая недельная матрица** с тремя уровнями просмотра — магазины, категории,
  артикулы. Один экран, переключатель, без дерева строк. Фильтры: магазин, ниша
  и категория, поиск, отбор строк по статусу Shortage / Overstock / ОК — итоги и KPI
  пересчитываются по показанной выборке. Строки приходят страницами по двести
  и догружаются при прокрутке, а в DOM живут только видимые: тысяча позиций
  открывается так же быстро, как два десятка.
- **Расчётное ядро:** исходный и адаптированный прогноз, реальный и адаптированный
  сток, DIFF, поставки, статусы OVER/SHORT. Правка прогноза сразу пересчитывает
  остатки, риски дефицита и закупку.
- **Закупочная потребность:** дата и объём заказа по исходному спросу с учётом
  остатков, партий в пути, lead time, MOQ, PCB, coverage и safety; результат в штуках,
  рублях, м³ и неделе прихода. Экран группирует позиции по поставщикам с итогами по
  группе, отмечает просроченные и ближайшие заказы и по каждой строке раскрывает
  разбор количества по слагаемым формулы.
- **Загрузка WB:** адаптер с фикстурным и HTTP-клиентом, нормализация в недельные
  факты, идемпотентный upsert, журнал синхронизаций.
- **Правки прогноза:** поячеечные и массовые (×%, +шт, задать, сбросить, перенос
  спроса между неделями) — всё с журналом корректировок.
- **Справочные страницы:** базовый потенциал SKU с ориентиром по факту и сезонность
  категорий по неделям.
- **График выбранной строки:** спрос по неделям с заштрихованной частью, которую не
  покрывает сток, и линия стока, уходящая ниже нуля при дефиците. Открывается щелчком
  по названию строки на любом из трёх уровней. Следующий щелчок по другой строке
  добавляет её на тот же график: до четырёх строк сравниваются линиями, с переключателем
  «в штуках / доля от собственного максимума».
- **Заказы поставщикам:** черновик собирается из группы на экране закупки, статусы
  черновик → размещён → принят / отменён. Размещённый заказ становится товаром в пути,
  и потребность уменьшается на него сама; отменённый возвращает её обратно.
  В черновике правятся количество, неделя прихода и примечание поставщику, лишняя
  позиция убирается; размещённый заказ только читается — его отменяют и собирают
  заново. Заказ выгружается в XLSX — шапка, строки и итоги, готовые к отправке
  поставщику.
- **Выгрузка в Excel:** матрица по текущему уровню и фильтрам (все показатели по
  неделям, закрытые недели выделены, автофильтр) и закупочный план, в котором разбор
  количества стоит колонками — спрос окна, страховой запас, остаток, партии в пути.
  Файл собирается тем же сервисом, что отдаёт экран, поэтому разойтись им негде.
- **Журнал корректировок** в двух режимах: по операциям, где массовая правка — одна
  строка, и по ячейкам, где видно прежнее и новое значение.
- **Права доступа:** роли просмотр / редактирование / администратор, сессия
  в httpOnly-куке, автор правки берётся из сессии, а не из запроса. У администратора
  есть экран пользователей: завести, сменить роль, отключить, задать новый пароль.
  Учётные записи не удаляются — журнал правок подписан именем автора.

Что ещё не сделано и почему — в бэклоге, по эпикам и с открытыми вопросами к заказчику.

## Устройство

```
backend/   FastAPI + SQLAlchemy + PostgreSQL (в разработке — SQLite)
  app/calc/          чистое расчётное ядро: ни БД, ни HTTP
  app/services/      сборка матрицы, закупки, правок
  app/api/           HTTP-слой
  app/integrations/  Wildberries
frontend/  React + TypeScript + Vite
docs/      ТЗ, архитектура, спецификация формул, тест-кейсы
```

## Запуск

Нужны Python 3.11+ и Node 20+. PostgreSQL не обязателен: по умолчанию используется
SQLite в файле `backend/raketa.db`.

**Бэкенд**

```bash
cd backend
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements-dev.txt   # Linux/macOS: .venv/bin/python
.venv/Scripts/python -m app.seed --reset                      # схема + демо-данные
.venv/Scripts/python -m uvicorn app.main:app --reload --port 8000
```

Каталог можно размножить для проверки на объёме — таблица на тысячах строк
показывает только видимые блоки, и увидеть это на восемнадцати позициях нельзя:

```bash
.venv/Scripts/python -m app.seed --reset --scale 60 --fixtures-dir ../tmp-fixtures
```

Ключ `--fixtures-dir` уводит сгенерированные выгрузки WB в сторону, чтобы не
переписать фикстуры репозитория. Отдельную базу задаёт `DATABASE_URL`.

Без демо-данных схему разворачивает `alembic upgrade head`. Приложение миграции
не применяет само: на старте оно проверяет ревизию и падает с подсказкой, если база
устарела. Подробности — [docs/06-migrations.md](docs/06-migrations.md).

Документация API — http://127.0.0.1:8000/docs

**Фронтенд**

```bash
cd frontend
npm install
npm run dev
```

Интерфейс — http://localhost:5173, запросы к API идут через прокси Vite,
поэтому отдельный базовый URL настраивать не нужно.

Вход обязателен. Демонстрационные учётные записи — по одной на каждую роль — заводит
сид, их почта и пароли перечислены в `backend/app/seed.py` (список `DEMO_USERS`).
Роли и настройки безопасности — [docs/07-auth.md](docs/07-auth.md).

**Проверки**

```bash
cd backend && .venv/Scripts/python -m pytest && .venv/Scripts/python -m ruff check .
```

```bash
cd frontend && npm run build
```

## Настройки

Все переменные необязательны, значения по умолчанию — в `backend/app/config.py`.

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `DATABASE_URL` | `sqlite:///./raketa.db` | В проде — `postgresql+psycopg://user:pass@host:5432/raketa` |
| `WB_CLIENT` | `fixtures` | `fixtures` — локальные файлы, `http` — реальный API WB |
| `WB_TOKENS` | пусто | `store01=<токен>,store02=<токен>` — ключи кабинетов, в базе не хранятся |
| `CORS_ORIGINS` | `http://localhost:5173,...` | Разрешённые источники |
| `SECRET_KEY` | небезопасный ключ для отладки | Подпись сессионных токенов; вне отладки обязателен |
| `SESSION_TTL_HOURS` | 12 | Срок жизни сессии |
| `COOKIE_SECURE` | `false` | Отдавать сессионную куку только по HTTPS; в проде обязательно `true` |

PostgreSQL для локальной разработки поднимается через `docker compose up -d db`.

## Состояние проекта

Это рабочая первая итерация, а не готовая к эксплуатации система. Главное, чего
не хватает для приёмки:

- Алгоритм DIFF и правила статусов OVER/SHORT реализованы как обоснованные
  допущения — их нужно сверить с действующими файлами заказчика (вопрос Q-1).
- HTTP-клиент WB написан, но не проверен на боевых ключах: кабинеты ещё не переданы
  (вопрос Q-3).
- Свой пароль человек сменить не может: новый задаёт администратор и передаёт
  лично. Сброса по почте нет (задача G-8).
- Расчёт идёт по всей выборке на каждый запрос: на 1080 позициях это 0,65 с из
  0,88 с ответа, и дальше линейно. Постраничная выдача это не лечит — нужен кэш
  или материализация, а для выбора стратегии нужны реальные объёмы (вопрос Q-9,
  задача G-6).
- Заказ выгружается файлом, но отправляет его человек сам: интеграции с почтой
  и печатной формы нет. Забытую позицию в готовый черновик не добавить — её заказывают
  вторым документом тому же поставщику (задача B-13).
- Выгрузка односторонняя: правки, сделанные в скачанном файле, обратно не загружаются.
  Нужна ли такая загрузка, зависит от того, как заказчик собирается прожить переходный
  период с Google Sheets (вопрос Q-13).
- Набор статусов заказа, запрет на правку размещённого заказа и правило «просроченное
  закрываем с недели прихода» — обоснованные допущения, их нужно подтвердить
  у заказчика (вопросы Q-11, Q-12).
- Вход не ограничен по частоте попыток: перебор замедляет только стоимость bcrypt.

Полный перечень с приоритетами — в [BACKLOG.md](BACKLOG.md).
